## 一、结论摘要

| 认证方式 | SDK 现状 | 判定 |
|---------|---------|------|
| 密码登录（SecurePassword） | `loginSecure`（PBKDF2 600k + HMAC challenge-response + 服务端盐） | ✅ **已适配**（V4.5 起） |
| 密码登录（明文 mock） | `loginAs`（明文过 SSL） | ✅ 已具备（开发环境） |
| 外部 IdP 登录（联邦） | `loginByExternal` + `externalSession` 双形态会话 + `refreshJwt` 续期 + `resolveOAuthCallback` | ✅ **已适配**（V1.0.12） |
| 短信登录（平台 GraphQL mutation） | `loginBySms(mobile, captcha)` | ⚠️ **旧形态**——字段名/参数名面向 AuthCenter 旧 GraphQL mutation，DMP 新流程为非 GraphQL 端点 |
| **短信 + CAPTCHA 门禁流（SmsCode/Captcha v0.1.0）** | **无取题/作答/门禁组合辅助** | ❌ **缺口①**（便利性首选） |
| 票据 SPA 兑现（/login/ticket） | **无 loginByTicket** | ❌ **缺口②** |
| 业务兑票（/login/ticket/redeem） | **无 redeemTicket** | ❌ **缺口③** |
| 票据换令牌 PKCE（/ticket/exchange） | **无误 exchangeTicket + code_verifier 生命周期** | ❌ **缺口④** |
| Refresh 续期（rotation） | `refreshJwt`（REST 双收键 `refresh_token`/`refreshToken`） | ⚠️ 部分（JWT 会话续期 ✅；平台 GraphQL refresh 不适用——REST 为主） |
| Logout | `logout()`（Bearer 携带） | ✅ 已适配 |
| 令牌内省 verify | 401 → AUTH_EXPIRED 引导重登 | ✅ 语义已覆盖 |
| 密码找回 / 改密（三通道） | 门面级（无内建端点，消费方自建） | ⚠️ 消费方自建（PBKDF2 能力已具备） |
| MFA（TOTP/SMS/恢复码） | 无内建端点（编排归消费方） | ⚠️ 消费方自建（无 SDK 直接需求） |
| 错误信封（ProblemDetails/DMP 简信封） | `toErrorCode` 双轨（V1.0.13/1.0.15） | ✅ 已适配 |
| 429/Retry-After 统一 | `RATE_LIMITED` 映射 | ✅ 已具备 |

**一句话**：**密码 / 外部 IdP / 错误信封 / 会话管理已全面适配**；最大缺口在 **SmsCode+Captcha 短信门禁流**（DMP 2026-11 交付、前端已预留待接）与 **票据族三端点**（/login/ticket、redeem、PKCE exchange）。

## 二、已适配能力核验（V1.0.15 代码证据）

### 2.1 SecurePassword 密码登录 ✅

`loginSecure(userName, password, { crypto?, iterations?, onProgress? })`：
1. `requestChallenge`（query）取 `challengeToken + salt + iterations`（服务端下发的盐——每登一次新盐）
2. `AuthCrypto.pbkdf2(password, salt, iters)`（默认 600_000，SHA256，32B 盐/32B 哈希 hex）
3. `AuthCrypto.hmac(clientHash, challengeToken)`（HMAC challenge-response）
4. `loginByContext(userName, response, { authType: "SECURE_PASSWORD", authInfo: challengeToken })` 提交

覆盖扩展仓 #1/#14/#15（密码登录/找回/改密均客户端算哈希）——**服务端零明文契约完整满足**。`AuthCrypto`/`pbkdf2`/`randomSalt` 已导出（可复用于找回/改密自建端点）。

### 2.2 外部 IdP 登录（联邦）✅

`loginByExternal(channelType, parameters)` → `ExternalLoginResult{ accessToken, refreshToken, expiresAt }` 持久化 `externalSession`（V1.0.12 双形态会话，与 sessionKey 互斥）；`refreshJwt()` 显式续期（4xx → `JWT_SESSION_INVALID` 清会话强制重登；网络失败保留）；Bearer 头自动携带（`transport.bearerToken`）；`resolveOAuthCallback(url)` 解析 code/state。

覆盖扩展仓 #5/#6（外部 IdP + 静默授权）——微信/QQ/支付宝/OIDC 认证书回调解析、会话形态、续期失败处理**完整**。

### 2.3 错误信封双轨 ✅

- **DMP 简信封**（`{error, message}`）：v1.0.15 `toErrorCode` REST 分支 `body.error` 原样透传（此前 400/403 业务码被丢弃恒 UNKNOWN——DMP 免登录/建档/兑票端点 P1-4 缺口已修复）
- **平台 ProblemDetails**（`errorCode` 扩展字段）：⚠️ **半适配（P0-2）**——`toErrorCode` 对 `body.errorCode` 仅认 4 个硬编码值（`domain-client-error.ts` L55-56 401 分支认 AUTH_FAILED/AUTH_REQUIRED；L65-71 400 分支认 INVALID_ARGUMENT/JWT_SESSION_INVALID）；v1.0.15 透传分支读的是 `body.error`（L109）——ProblemDetails 信封**没有 `error` 键**。票据族错误码（`TICKET_INVALID`/`ACCOUNT_FROZEN`/`ACCOUNT_DISABLED`/`TICKET_RATE_LIMITED`）经 SDK REST 通道全部落 **UNKNOWN**。**须升格为前置缺口项**（对齐 v1.0.15 `body.error` 透传形态，新增 `body.errorCode` 通用透传分支——票据族缺口②③④的错误语义依赖；版本归属：errorCode 分支实为 v4.8.7（401）+ v1.0.12（400）引入，v1.0.13 为 error-codes 码表同步，P2-7）
- 429 → `RATE_LIMITED`（两端共用语义）；401 区分 `AUTH_REQUIRED`/`AUTH_FAILED`/`AUTH_EXPIRED`——⚠️ **Retry-After 未适配（P1-3）**：`toErrorCode` L74 429 固定状态映射优先于 body 透传，且 `base-http-transport.ts` L116-117 429 分支**丢弃 body 与 headers**（全 src 对 `Retry-After`/`retryAfter` 零命中）——send-code 429 body 的 `retryAfterSeconds` 不可达

## 三、缺口与便利性机会（待 Oracle 评审判定）

### 缺口①（首选）：SmsCode + Captcha 短信门禁流

**现状**：`loginBySms(mobile, captcha)` 的参数名 `captcha` 是**旧 AuthCenter GraphQL mutation 形态**（`loginBySms` 字段 + `{mobile, captcha}` 变量）——与 DMP 最新流程语义冲突：DMP 的 `captcha` 含义已变为 **CHAPTCHA 图形码凭据**（`{challengeId}:{answer}` 组合串），且登录三步骤为：
1. `POST /m/{mid}/api/auth/sms/chaptcha`（取题：`{challengeId, payload(SVG), ttlSeconds}`）
2. `POST /m/{mid}/api/auth/sms/send-code`（body `{mobile, chaptcha: "{challengeId}:{answer}"}` → `{sent, retryAfterSeconds}`）
3. `POST /m/{mid}/api/auth/sms/login`（body `{mobile, code}` → IdentitySession）

**便利性提案**（v1.1.0 候选；⚠️ 端点归属 P1-5：`/m/{mid}/api/auth/sms/*` 三端点为 **DMP Merchant.WebApi 手写 MapPost 挂接的消费方装配端点**（扩展零端点），与平台 AuthCenter `{prefix}/sms/send-code`（body `{phone, scene}`）**是两套不同契约**——实现路径为 `transport.execute({field: "auth/sms/..."})`（REST transport 经 restPathPrefix 映射；DMP `scenario.ts` 实证可达）+ urlMap 可覆盖；GraphQL transport 下不适用）：
- `loginBySmsCode<T = unknown>(mobile, code): Promise<T>`（P1-4 修正：**泛型返回 + 不持久化 SDK 会话**——IdentitySession 是 DMP 接入主体契约（H5 指南契约归属警告，tenant/membership/nextAction/capabilities 为 DMP 业务概念），内嵌类型 = 消费方契约泄漏进平台 SDK；落盘归消费方；保留旧 `loginBySms` 并在两方法 JSDoc 互相指向——wire 目标不同（GraphQL 平台 mutation vs DMP REST 契约），命名近似是真实风险点）
- `issueChaptcha(): Promise<{challengeId, payload, ttlSeconds}>`（field "auth/sms/chaptcha"；**payload 交由前端渲染**——P2-9：渲染不是 SDK 职责）+ 组串内化（P2-8）：**`sendSmsCode(mobile, challengeId, answer): Promise<{sent, retryAfterSeconds}>`**——三参形态下调用方接触不到 `"{challengeId}:{answer}"` 格式与 `chaptcha` 拼写（格式冻结 + 拼写陷阱双消除，wire 键正确性由 SDK 单点保证——DMP 前端预留 TODO 拼写即写错为 `captcha/captchaToken`）
- 429 处理（P1-3）：改造 429 分支读 body（`retryAfterSeconds` 挂 DomainClientError 扩展字段 + `body.error=rate_limited` 透传）或明确降级为「200 响应体 retryAfterSeconds 驱动倒计时、429 场景固定提示」——**二选一定稿时明示**（现状「Retry-After 语义已在 SDK 基础层」**不成立**）

### 缺口②：票据 SPA 兑现（/login/ticket）

**现状**：`/login/ticket`（V0.10.0——事件取 OpenId 链路"票 → token1"前端兑换面；null-claimant 票、`TICKET_INVALID` 统一判因、429/503）SDK **无 loginByTicket**。

**便利性提案**：`loginByTicket(ticket, channelId?)`（POST JSON body；成功 → sessionKey/token 建档同 loginByExternal 形态；`TICKET_INVALID` → 引导重新触发取票；**票消费后重试恒无效的 UI 语义**）。

### 缺口③：业务兑票 redeem（/login/ticket/redeem）

**现状**：V0.14.0（2026-11-11）业务兑票端点——验票 → L2 账号状态检查 → 返 `FederatedTicketPayload` 明文 11 字段 + extensions（**不建会话不发 token**）。SDK 无。

**便利性提案**：`redeemTicket(ticket)`（返回 payload 明文；`ACCOUNT_FROZEN`/`ACCOUNT_DISABLED` 400 分支提示——**注意冻结/禁用为 400 非 403**，SDK 不能按状态码硬判）。

### 缺口④：票据换令牌 PKCE（/ticket/exchange）

**现状**：`/ticket/exchange {ticket, code_verifier, app_id, state}`（TTL 5min 单次、PKCE 校验矩阵——**签发时存 verifier hash，换取时必填比对（trust 签发 hash null 可不传）**；双守卫冻结/禁用 400 票不消耗）。SDK 无。

**便利性提案**（P0-1 修正——PKCE verifier 语义）：`exchangeTicket(ticket, codeVerifier, appId, state?)`——**显式收 verifier 参数**（PKCE verifier 在**签发侧**就已确定存 hash，SDK 仅做换取侧——内部生成必不匹配恒 TICKET_INVALID；须由消费方在 authorize/签发时生成并自持，exchange 时回传）；另提供 `randomCodeVerifier()` 生成助手（对齐 `crypto.ts` randomSalt 形态，RFC 7636 unreserved 43-128 字符）；`TICKET_*` 错误码族细分支映射（依赖 P0-2 透传分支）；state 防重放管理；成功建 externalSession（TokenResponse 同 loginByTicket）。

### 便利性机会⑤：其他（评估项）

| 项 | 提案 | 优先级 |
|---|------|--------|
| 会话双形态统一 | **不做（评审答复 3 裁定——双轨不统一）**：IdentitySession 是 DMP 接入主体契约（H5 指南 L83 契约归属警告），LoginPayload 是平台 GraphQL 契约，ExternalSession 是 SDK 内部 JWT 会话形态——三者服务不同层；SDK 保持平台形态 + 泛型开放消费方形态 | —（closed） |
| 密码找回/改密客户端辅助 | 复用 `AuthCrypto.pbkdf2`（已导出）+ 提供 `resetPasswordSms()`/`changePassword()` 便捷封装（面向 DMP 自建端点） | 中 |
| MFA 辅助 | otpauth:// URI 解析（供 QR 渲染）+ 恢复码一次性展示组件建议（编排仍归消费方） | 低 |
| verify 内省 | `getSessionInfo()`（GET /verify 200 {valid,userId,authType,...}——401 显式重登语义已在基础层） | 低 |
| 错误码全集 | 扩展仓错误码 delta 同步（`sms_rate_limited`→`rate_limited`、send-code 400→429、新增 `chaptcha_failed`/`sms_sender_unavailable`/`invalid_scene`——经 v1.0.15 `body.error` 透传**已可达**，非新枚举而是类型文档 + 测试断言；票据族错误码随 P0-2 透传分支） | 中（随缺口①） |
| 联邦子应用委托流（authorize/start、oauth callback、trust/issue、identity/claim） | **不适用（P2-10）**——后端编排为主（子应用后端发起 + 302 重定向回子应用），前端 SDK 无直接需求；全景表补完备性行 | — |
| 平台 /grants、/sms/verify | **暂缓（P2-10）**——已有端点、低优先内省/独立校验面（/verify 语义已覆盖；/grants 授权管理页按需） | 低 |

| 条件 | 严重度 | 修订 |
