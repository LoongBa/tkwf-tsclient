## 1. 缺陷背景（已逐条源码核实）

| # | 断言 | 核实结果 | 源码证据 |
|---|------|---------|---------|
| 1 | Use<T>() 带复杂 DTO 入参 → HotChocolate 400 `The variable request is not compatible with the type of the current location` | ✅ 逻辑证成 | ServiceProxy.createUse 的 `transport.execute({ field, type, variables, selection, sessionKey, signal })` 六字段**无 variableTypes**（`src/service-proxy.ts:74-81`）；`inferGraphQLType(object)` 退回 `"JSON"`（`src/transport.ts:165`）→ 文档生成 `($request: JSON)`，与后端 `GetRankingsReqDtoInput!` 位置不兼容 |
| 2 | transport.ts L92 已支持 variableTypes | ✅ | `Transport` 接口 L56 + `GraphQLTransport.execute` L81/86/92：`variableTypes?.[v] ?? inferGraphQLType(...)` |
| 3 | SDK 内置登录不受影响（硬编码 variableTypes） | ✅ | `src/domain-client-user.ts:202` `{input:"LoginContextInput!"}`、L302 `{input:"RegisterSecureInput!"}`——直接调 transport，不经 ServiceProxy |
| 4 | codegen 无 operationVariableTypes 映射 | ✅ | `operationVariableTypes` 全仓库 0 匹配；`ParsedOperation.args`（`schema-parser.ts:22-28`）已含 `gqlType/isNonNull/isList`，生成所需信息**齐备** |
| 5 | 影响：带 DTO 入参命名操作全 400 | ⚠️ 条件性成立 | 前提：后端参数为具体 input type（HotChocolate 对 DTO 参数的默认生成，成立）；若后端参数声明为 `JSON` 标量则不报错 |

**修复方向（已确认）**：transport 层零改动；补齐 ServiceProxy 链路（构造接收 + execute 透传）+ 逐级透传入口（host → user → proxy，仿 selectionMap 现有链路）+ codegen 提供 `operationVariableTypes` 生成能力 + 测试。

## 2. 设计

### 2.1 数据流（完全对齐 selectionMap 现有链路）

```
Tkwf.configure({ variableTypesMap })      ← TkwfConfig extends DomainHostClientOptions（tkwf.ts:22，自动继承）
  → DomainHostClientOptions.variableTypesMap?        （domain-host-client.ts，JSDoc 对齐 L59-64）
  → GetUser()/GetGuest() 构造 DomainClientUser        （domain-host-client.ts:202/229）
  → DomainClientUserOptions.variableTypesMap?         （domain-client-user.ts:37-55）
  → Use<T>() 构造 ServiceProxy                        （domain-client-user.ts:450-459）
  → ServiceProxyOptions.variableTypesMap?             （service-proxy.ts:23-36）
  → createUse() 派生本次调用 variableTypes            （service-proxy.ts:55-105）
  → transport.execute({ ..., variableTypes })          （transport.ts:92 消费）
```

**命名**：`variableTypesMap`（对齐 `selectionMap` 命名风格，避免与 execute 形参 `variableTypes` 混淆）。

### 2.2 ServiceProxy 层（核心修复）

```typescript
export interface ServiceProxyOptions {
  // ... 现有字段
  /** Map of GraphQL field names to their per-variable GraphQL type declarations.
   *  e.g. { rankings_Execute: { request: "GetRankingsReqDtoInput!" } }
   *  Generated by codegen（`operationVariableTypes`，与 selectionMap 同源同代）。
   *  When provided, the proxy passes them through to Transport.execute(). */
  variableTypesMap?: Record<string, Record<string, string>>;
}

// createUse() 内：
const options = args.length > 1 && typeof args[1] === "object" && args[1] !== null
  ? (args[1] as { signal?: AbortSignal; selection?: string; variableTypes?: Record<string, string> })
  : undefined;
const sel = options?.selection ?? this.selectionMap?.[field];
const variableTypes = options?.variableTypes ?? this.variableTypesMap?.[field];   // 新增
// execute 透传：
this.transport.execute({ field, type, variables, selection: sel, variableTypes, sessionKey, signal });
```

- **调用方显式覆盖**：args[1] options bag 扩展 `variableTypes?`（对齐 `selection` 已有先例——`options.selection ?? selectionMap[field]`，L69）。修订说明（Oracle S3）：JSDoc 注明该覆盖**主要用于与 selection 的对称性**——变量类型由 schema 决定、由 codegen 产出，运行时逐调用覆盖非预期用法，避免消费端误用。`Transport.execute` 结构类型要求 `variableTypes?` 已含（transport.ts:56），无类型问题。
- 未配置/未命中时 `variableTypes === undefined` → transport L92 落回 `inferGraphQLType`，行为与现状完全一致（向后兼容）。

### 2.3 DomainClientUser / DomainHostClient 透传

- `DomainClientUserOptions.variableTypesMap?`：JSDoc 说明"Passed through to ServiceProxy for Use() variable type declarations."
- `DomainHostClientOptions.variableTypesMap?`：JSDoc 对齐 selectionMap（L59-64）——"Generated by codegen（`operationVariableTypes` in domain-client.g.ts）。"构造存储 + GetUser/GetGuest 透传。
- REST 通道无影响：RestTransport 实现忽略 `variableTypes`（GraphQL 专有），透传 undefined 语义不变。

### 2.4 codegen：`buildVariableTypesMap`（能力提供）

本仓库 codegen 不产出 `domain-client.g.ts`（生成器在消费端链路），但 `schema-parser.ts:3` 明确"供消费端同时驱动 ts-client.g.ts 和 GraphQL_Api.md 生成"——故在 `schema-parser.ts` 新增**纯函数**供消费端生成器调用：

```typescript
/** 由 ParsedSchema 构建操作→变量→GraphQL 类型映射（供消费端 g.ts 生成器输出 variableTypesMap）。
 * 修订说明（Oracle S1）：命名从 buildOperationVariableTypes 调整为 buildVariableTypesMap，
 * 与产出物 option 名 variableTypesMap 直接对应。 */
export function buildVariableTypesMap(
  parsed: ParsedSchema,
): Record<string, Record<string, string>> {
  const out: Record<string, Record<string, string>> = {};
  for (const op of parsed.operations) {
    if (op.args.length === 0) continue;
    const vars: Record<string, string> = {};
    for (const arg of op.args) {
      vars[arg.name] = toGraphQLTypeString(arg);
    }
    out[op.name] = vars;
  }
  return out;
}
```

**类型重建规则**（精确还原 schema 声明，避免"声明≠位置"二次 400）——覆盖**全部 4 种列表可空性组合**（修订说明 Oracle M1：原规则表遗漏"外层可空 + 元素非空"的 `[T!]`）：

| isNonNull（外层） | listElemNonNull | 拼接 | 示例 |
|---|---|---|---|
| true | true | `[${gqlType}!]!` | `[Int!]!` |
| true | false | `[${gqlType}]!` | `[Int]!` |
| false | true | `[${gqlType}!]` | `[Int!]` |
| false | false | `[${gqlType}]` | `[Int]` |
| —（非列表） | — | `${gqlType}${isNonNull ? "!" : ""}` | `GetRankingsReqDtoInput!` / `Int` |

具体实现（`toGraphQLTypeString`）：

```typescript
function toGraphQLTypeString(arg: ParsedArg): string {
  if (!arg.isList) return `${arg.gqlType}${arg.isNonNull ? "!" : ""}`;
  return `[${arg.gqlType}${arg.listElemNonNull ? "!" : ""}]${arg.isNonNull ? "!" : ""}`;
}
```

**ParsedArg 扩展 `listElemNonNull?: boolean`**：现有 `stripWrapper`（`schema-parser.ts:72-99`）已剥离"列表元素非空"但**丢弃**该信息（只返回 `isList` 布尔）。为无损重建需保留——`stripWrapper` 返回值增加 `listElemNonNull`，`parseArg` 透传。**新增可选字段，向后兼容**（现有消费者不受影响；`ParsedField` 不动——DTO 字段类型重建不属于本迭代）。

### 2.5 消费端接线（不在核心实现，README 提供说明）

消费端 g.ts 生成器在产 `operationSelection` 处追加 `operationVariableTypes`：

## 6. 向后兼容与开放项

**向后兼容**：
- 全部新增项均为**可选字段**（`variableTypesMap?` / `listElemNonNull?` / `variableTypes?`），未配置时 `variableTypes === undefined`，transport 落回 `inferGraphQLType`——行为与 v1.0.9 完全一致
- `Transport` 接口、REST 通道、缓存层、QueryBuilder 零改动
- `TkwfConfig` 自动继承新选项，无 API 破坏
- 现有 302 条测试不回归

**开放项（不在本迭代范围）**：
1. **消费端 g.ts 生成器接入**：本迭代在 SDK 侧提供 `buildOperationVariableTypes` 能力；消费端生成器（不在本仓库）需在生成 `operationSelection` 处同步输出 `operationVariableTypes` 并传入 `configure`。SDK 文档/README 提供接线说明，真实接入验证依赖消费端项目。
2. **selectionMap 与 variableTypesMap 合并为单映射**：两者同源同代（codegen 一次解析），未来可在消费端生成器封装为 `{ field: { selection, variableTypes } }` 单对象；本迭代保持分离、最小改动，不做结构重构。
3. **`generateGraphQLApiDoc` 输出 variableTypes 列**：文档操作清单目前以 TS 类型呈现参数（`formatArgs`），GraphQL 输入类型对前端消费文档非必需；留待需要时追加，不在本迭代。
