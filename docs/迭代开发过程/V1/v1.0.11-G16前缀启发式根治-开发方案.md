## 1. 缺陷背景与设计原则对照

### 1.1 缺陷根因（已逐条源码核实）

| # | 断言 | 核实结果 | 源码证据 |
|---|------|---------|---------|
| 1 | 服务端 SG 把 `Xxx_ExecuteAsync` 判为**非 mutation** → 所有 `*_Execute` resolver 字段进 GraphQL Query 根（稳定事实，非缺陷） | ✅ | XiaoShuTong schema.graphql 实证（`removeBuddy_Execute` L44 / `createTask_Execute` L121 均在 Query 段；Mutation 根仅 8 认证/AI 字段）；P1 方案 Oracle 否决"框架加 Execute 前缀"（双向恶化 + 生态破坏性变更） |
| 2 | SDK `isMutation()` 前缀启发式把 `remove*/create*` 判为 mutation → 发 `mutation { removeBuddy_Execute }` → HTTP 400 | ✅ | `src/service-proxy.ts:5-14`：`MUTATION_PREFIXES` + 2 参 `isMutation`；`createUse()` L72 消费 |
| 3 | **codegen 产物已含权威 type 标记，SDK 不消费（根因锚点）** | ✅ | 消费端 ts-client.g.ts 已有 `export const Query = { createBank_Execute: { field, type: 'query' } as const }` / `Mutation` 常量（XiaoShuTong `src/gql/ts-client.g.ts:7,79` 实证）；生成器 `gen-ts-client.ts:741-747` 从 schema **权威提取** `type:'query'|'mutation'`（`extractFieldInfos(schema,'Query'/'Mutation')`）；SDK `explicitQueries` 全仓库 0 命中 |
| 4 | 现有 `explicitMutations` 逃生口是**加性覆盖**且硬编码脆弱 | ✅ | `src/domain-client-user.ts:482-489` `EXPLICIT_MUTATIONS` 硬编码 6 项（注释"MUST be kept in sync with the schema's Mutation type"）；v1.0.4 误列 requestChallenge/registerSecure 被删（commit `9d8d7b4`） |
| 5 | 影响面 | ⚠️ 实证 | XiaoShuTong 3 处实际 400 + 4 处潜在 + V0.8.1 新暴露 `updateTask_Execute`；已用 `sdk-bypass.ts` 绕行 |
| 6 | **REST 通道**：`type` 同时驱动 RestTransport HTTP 方法 | ✅ | `src/rest-transport.ts:110`：`method = type === "query" ? "GET" : "POST"`——type 翻转会改变 REST 消费端 GET/POST 路由（见 §2.6） |

### 1.2 设计原则对照（为什么双集合补丁不是全局最优，为什么本方案是）

| TKWF 原则 | 双集合补丁方案（explicitQueries + explicitMutations） | **本方案（operationKinds 单映射契约驱动）** |
|---|---|---|
| **P1 编译期确定性优先于运行时反射** | 运行时用 Set 成员判定 + 前缀启发式兜底——正确信号编译期已生成（ts-client.g.ts type 标记），却被降维成运行时双集合 + 运行时猜测 | codegen 在**生成期**权威产出 `operationKinds` 单映射（`{ field: 'query'/'mutation' }`），SDK 运行时**纯读取零猜测** |
| **P2 唯一权威事实源，下游纯消费** | 三机制并存：explicitQueries + explicitMutations + 启发式——**SDK 另立第二/三判定源**（`MUTATION_PREFIXES` 即"脆弱启发式替代契约"） | 单一链路：schema 根类型 → 生成器（`gen-ts-client.ts` 已提取）→ `operationKinds` → SDK 纯消费；启发式**废弃** |
| **P7 缺省=守卫硬失败，不静默失效** | 未接线消费端**静默**走启发式——正是错误模式"静默失败/静默 return" | 未配置 `operationKinds` 且字段落启发式 → **dev 显式告警**（`console.warn` 单次去重，可配置关闭）——废弃路径显式暴露 |
| 错误模式"脆弱启发式替代契约"（ADR94 先例） | 保留启发式为默认路径，补丁式 | **启发式降为废弃兜底**，契约（operationKinds）为主路径——对齐 ADR94（G20 权威注册选择契约化）先例 |
| 元原则（先例可能错） | 迁就既有 `explicitMutations` 逃生口设计 | 以全局最优为判据：`operationKinds` 单映射（Oracle 第一轮 S1 已指出"更简洁"），`explicitMutations` 仅作未接线向后兼容兜底 |

**结论**：G16 是"生成物与运行时不闭环"——框架生成体系（SG/codegen 三层契约）已产出正确信号，SDK 运行时另立启发式破坏闭环。全局最优解 = **SDK 收敛为纯消费方（P2 下游纯消费），编译期知识不降维、不重推、不猜测（P1），废弃路径显式暴露（P7）**。

### 2.2 ServiceProxy 层（核心修复——纯消费）

```typescript
/**
 * V1.0.11（G16 根治）判定顺序：
 *   1. operationKinds?.[name]                权威映射（codegen 产物，'query'/'mutation' 均命中即返回）
 *   2. explicitMutations?.has(name) → true   向后兼容兜底（SDK 内置登录 + 老消费端显式配置）
 *   3. MUTATION_PREFIXES 前缀启发式         废弃兜底（未接线老消费端；命中即 console.warn 单次）
 * 未配置 operationKinds 时行为与 v1.0.10 一致（仅新增废弃告警信号，不改判定结果）。
 */
function isMutation(
  name: string,
  operationKinds?: Readonly<Record<string, "query" | "mutation">>,
  explicitMutations?: ReadonlySet<string>,
): boolean {
  const kind = operationKinds?.[name];
  if (kind === "mutation") return true;
  if (kind === "query") return false;
  if (explicitMutations?.has(name)) return true;
  return heuristic(name); // deprecated
}
```

- **无优先级歧义**：`operationKinds` 单值判定（每字段一个权威值），codegen 产物天然互斥——不存在双集合冲突问题（第一轮方案的 explicitQueries-vs-explicitMutations 优先级规则整体消失）。
- **`explicitQueries` 概念并入 `operationKinds`**：`operationKinds[name] === 'query'` 即反向白名单（服务端 Query 根字段），不再新增独立 API（比第一轮方案更收敛，符合 P2 单一权威源）。
- **启发式废弃告警（P7）**：

```typescript
let heuristicWarned = false;
function heuristic(name: string): boolean {
  if (!heuristicWarned) {
    heuristicWarned = true;
    console.warn(
      `[@tkwf/tsclient] operationKinds 未配置（或未覆盖字段 "${name}"），` +
      `正在使用废弃的 MUTATION_PREFIXES 前缀启发式判定操作类型——` +
      `请接入 codegen 产物 operationKinds（见 README V1.0.11 接线说明）。`,
    );
  }
  const lower = name.toLowerCase();
  return MUTATION_PREFIXES.some((p) => lower.startsWith(p));
}
```

  - **单次去重**（module 级 flag）——不刷屏；**可配置关闭**（`ServiceProxyOptions.suppressHeuristicWarning?`，Tkwf.configure 透传）——生产环境可静默；**不改判定结果**——未接线行为与 v1.0.10 完全一致，仅新增显式信号。
- **`ServiceProxyOptions` 新增**：
  - `operationKinds?: Readonly<Record<string, "query" | "mutation">>` —— 主权威映射
  - `suppressHeuristicWarning?: boolean` —— 关闭废弃告警（默认 false 即默认告警）
  - `explicitMutations?` 保留（向后兼容 + 未接线兜底）
- `MUTATION_PREFIXES` 标 `@deprecated`；`graphql-api-doc.ts` 副本**不动**（文档分组启发式，登记开放项）。

### 2.5 codegen：`buildOperationKinds` 纯函数（能力提供，对齐 buildVariableTypesMap v1.0.10 先例）

```typescript
/** 由 ParsedSchema 构建操作→类型单映射（供消费端生成器输出 operationKinds）。
 *  数据源为 schema 根类型权威判定（ParsedOperation.kind，schema-parser L296）。
 *  对称于 buildVariableTypesMap（v1.0.10）。 */
export function buildOperationKinds(
  parsed: ParsedSchema,
): Record<string, "query" | "mutation"> {
  const out: Record<string, "query" | "mutation"> = {};
  for (const op of parsed.operations) out[op.name] = op.kind;
  return out;
}
```

- **消费端生成器接入两条路径**（README 说明，非本仓库代码）：
  - **路径 1（推荐）**：使用 SDK `schema-parser` 的生成器 → `buildOperationKinds(parsed)` 产出（对齐 `buildVariableTypesMap` 既有接线）。
  - **路径 2（XiaoShuTong 自研生成器）**：`gen-ts-client.ts` 已有 `queryFields`/`mutationFields`（带 type）——在生成 Query/Mutation 常量处追加 `export const operationKinds` 从两者合并派生（约 5 行，权威数据已在 L741-747）。
- **存量产物零依赖**：未升级生成器的消费端不产出 operationKinds → SDK 走 explicitMutations + 启发式兜底（行为不变 + 废弃告警）。

### 2.6 消费端接线（README 说明，非本仓库代码）+ REST 通道影响

```typescript
// 消费端应用入口（如 main.tsx）——与既有 selectionMap/variableTypesMap 同源同模式
import { operationKinds, operationSelection, operationVariableTypes } from "./ts-client.g";

Tkwf.configure("default", {
  endpoint: "/graphql",
  operationKinds,                               // V1.0.11 G16 根治：权威操作类型映射（codegen 产物）

```

- 接入后：所有字段命中 `operationKinds` → **启发式永不触发**（对已接线消费端 = 消灭启发式，符合 G16 §四 方案 2"根治"语义）；未接线消费端完全不受影响（向后兼容 + 废弃告警显式暴露）。
- **REST 通道影响（Oracle M1，证据 `rest-transport.ts:110`）**：type 翻转（mutation→query）会改变 REST 消费端 HTTP 方法（POST→GET）。**显式影响面假设**：受影响字段均为 XiaoShuTong 领域方法，XiaoShuTong 走 GraphQL 通道——**当前无已知 REST 消费端调用这些字段**。登记开放项：未来若有 REST 消费端调用 Query-root 写方法，需评估服务端 SG2 REST 端点 HTTP 方法兼容（REST 端点动词固定，不随 GraphQL 根类型）。
- XiaoShuTong `main.tsx` 已接入同源 selectionMap/variableTypesMap（V0.7.7 实证），扩展 `operationKinds` 同模式即可；移除 `sdk-bypass.ts` 绕行 + 4 潜在方法验证为消费端验收动作（G16 §五 / P1 方案 M1 #2-5）。

- 全部新增项均为**可选字段**（`operationKinds?` / `suppressHeuristicWarning?`），未配置时 `isMutation` 走 explicitMutations + 启发式——判定行为与 v1.0.10 完全一致（唯一新增：启发式命中时 console.warn 单次，**不改判定结果**，可 `suppressHeuristicWarning` 关闭）

- `explicitMutations` API **保留**（已发布 API，向后兼容；新消费端用 operationKinds 主路径）
- `Transport` 接口、REST 通道实现、缓存层、QueryBuilder 零改动
- 现有 302 条测试不回归

**开放项（不在本迭代范围）**：
1. **`MUTATION_PREFIXES` 与 `EXPLICIT_MUTATIONS` 最终移除**：待主要消费端（XiaoShuTong/DMP-Lite 等）全部接入 `operationKinds` 后，在后续版本删除（含 `graphql-api-doc.ts` 副本，或该副本改为从权威 kind 数据分组）。
2. **消费端生成器接入与验收**：README 提供两条路径（`buildOperationKinds` / 自研生成器派生）；XiaoShuTong `gen-ts-client.ts` 追加 `operationKinds` 产物 + `main.tsx` 接线 + `sdk-bypass.ts` 移除 + 4 潜在方法验证 = 消费端侧验收（G16 §五 / P1 方案 M1 #2-5），依赖消费端迭代。
3. **tkwf-tsclient-mock 动词表漂移**（独立仓库）：`parse-service.ts:280` / `generate.ts:391` 等 4 处动词表与 SDK 不一致，且违背自身 v1.1.0"不再启发式推断"设计意图——另行小版本（v1.4.5）独立处理；其 handler-kind 判定可同模式改为消费 `operationKinds`（对齐 P2 纯消费）。
4. **REST 通道未来验证**：若未来有 REST 消费端调用 Query-root 写方法，评估 SG2 REST 端点 HTTP 方法兼容（REST 端点动词固定，不随 GraphQL 根类型）。
