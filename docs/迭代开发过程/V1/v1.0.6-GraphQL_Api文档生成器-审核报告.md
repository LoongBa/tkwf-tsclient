## 三、代码质量评审

### 3.1 模块边界

```
src/codegen/
├── schema-parser.ts        # 303 行 — 解析层（依赖 graphql 包）
├── graphql-api-doc.ts      # 318 行 — 渲染层（零 graphql 依赖）
├── schema-parser.test.ts   # 163 行 — 解析器测试（10 用例）
├── graphql-api-doc.test.ts # 174 行 — 渲染器测试（14 用例）
└── index.ts                # 12 行 — 模块入口
```

**边界清晰**：解析层（需 graphql）与渲染层（纯数据消费）完全分离。渲染层不 import 任何 `graphql` 类型，仅消费 `ParsedSchema` 纯数据接口。

### 3.2 类型安全

- 所有导出类型使用 `interface`/`type`（`erasableSyntaxOnly: true` 兼容）
- 类型导入使用 `import type { ... }`（`verbatimModuleSyntax: true` 兼容）
- 无 `as any`、`@ts-ignore`、`@ts-expect-error`（仅 `defaultValue` 提取处使用 `as any`，属 graphql AST 类型系统局限，已标注）
- 无冗余类型断言

### 3.3 测试覆盖率

| 层次 | 覆盖场景 |
|------|---------|
| 解析器 | 基础 Query/Mutation/非空/列表/DTO/Enum/描述/默认值/非法输入/空 schema/Input 类型 |
| 渲染器 | 文档骨架/标量返回/DTO 引用/ignoredFields/4 种暴露状态/分组 heuristic/groupOverrides/pageMapping/descriptions/scalarMap/blockingPages |
| 端到端 | `npm run build` + `npm test` 全量通过 |

### 3.4 代码重复

`parseField()` 与 `parseFieldFromInputValue()` 函数体完全相同，仅参数类型不同（`FieldDefinitionNode` vs `InputValueDefinitionNode`）。这是 TypeScript 结构类型系统的限制——两个类型虽有相同字段但 `kind` 不同，无法合并。**保留现状，不引入泛型抽象**（会导致 AST 类型松散）。
