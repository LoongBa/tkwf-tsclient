## 3. 逐文件代码审查

### 3.1 `src/event.ts`（新增）

- **类型**：`RpcEventData` / `RpcEventEnvelope` / `EventHandler` 与方案 §2.1 完全一致；`data: unknown` 保持契约严谨（框架侧"事件字段 JSON 化"未限定为对象）。
- **`parseRpcEventEnvelope`**：
  - ✅ 同时接受已解析对象与 JSON 字符串，字符串走 `JSON.parse` 且 try/catch 返回 `[]`（方案 §2.1 代码片段省略了 string 分支，但 §2.3.4 REST 路径明确传入解码后的 JSON 字符串且注释要求"内部 JSON.parse 必须 try/catch"——**实现已补上 string 分支**，是方案碎片的必要修正）
  - ✅ 整体非法返回 `[]`（null / 非对象 / `events` 非数组 / 畸形 JSON）
  - ✅ 逐条过滤：`name`/`type`/`timestamp` 非 string 跳过，合法条目保留
  - ✅ 可选字段：`data` 缺省 `{}`；`triggeredBy`/`correlationId` 非 string → `undefined`
- **`base64UrlDecode`**：
  - ✅ 三步：`-/_` → `+/`；补 padding `(4 - len%4)%4`；跨环境解码（`atob` 浏览器 / `Buffer.from(...).toString("binary")` Node）+ `TextDecoder("utf-8")` 还原
  - ✅ 无内部 try/catch（由 RestTransport 捕获，符合 Oracle M1"解码失败丢弃不阻断业务"）
  - ✅ 中文 UTF-8 round-trip 测试覆盖
- **`TkwfEventBus`**：
  - ✅ `Map<string, Set<EventHandler>>` 索引；`on` 返回退订函数；`off` 无 handler 时清理空 Set；`emit` 未注册事件静默 no-op；`dispatch` 防御空输入；`clear` 清空
  - ✅ Handler 抛错 try/catch 包裹走 `console.error`，不向外传播（事件派发不破坏主流程返回值）
  - ✅ **Oracle M1 守卫（审核落地）**：`emit` 入口 `if (!event || typeof event.name !== "string") return;`——畸形事件条目（如 GraphQL 侧信道 `events:[null]`）静默 no-op，禁止 `event.name` 抛 TypeError 穿透 `onResponse` 打断业务结果
- **`declare const Buffer`**：仓库未依赖 `@types/node`，为编译期提供最小类型，运行时仍取 Node 全局 `Buffer`。仅文件内局部作用，无全局冲突。工程上可接受（Oracle 核验：模块作用域绑定，不污染消费者全局）。

### 3.2 `src/transport.ts`

- ✅ `ResponseContext<T>` 增加可选 `events?: RpcEventData[]`，中文 JSDoc，无事件时 `undefined` —— 向后兼容（现有 `onResponse` interceptor 签名不变）
- ✅ `GraphQLTransport.extractEvents` 覆盖：读 `extensions.tkwf.events`，`Array.isArray` 守卫 + 空数组返回 `undefined`
- ✅ **Oracle S1 过滤（审核落地）**：GraphQL 路径与 REST 一致，`extensions` 经 `parseRpcEventEnvelope({ events: extensions })` 逐条过滤——畸形条目（null/缺 name）不进入 `res.events`、不暴露给用户 `onResponse`（实现期先传裸数组导致 4 项测试失败，已修正为 envelope 包装 `{ events: extensions }`，68 测试全过）
- ✅ `parseResponse` / `execute` / `executeRawGraphQL` 行为不变（业务结果原样透传，extensions 不污染 data）

### 3.3 `src/base-http-transport.ts`（核心改造，Oracle M2）

- ✅ ③ 段：`executeWithRetry<T>` 闭包改为返回 `{ data, json, headers }` 结构体——`json`（含 GraphQL extensions）与 `response.headers`（REST 侧信道）不再被闭包吞掉，④ onResponse 段可达
- ✅ 闭包内错误处理完整保留：AbortError→CANCELLED、TypeError→NETWORK_ERROR、401 映射、429、!ok——均与改动前一致，仅末行返回值形态变化；`parseResponse` 仅调用一次
- ✅ 基类新增 `protected extractEvents(_json, _headers)` 默认返回 `undefined`（用默认方法而非 `?` optional property，符合方案）
- ✅ ④ 段：`const events = this.extractEvents(json, headers)` → `...(events ? { events } : {})` 组装 `ResponseContext`（`satisfies` 类型守卫）
- ✅ `executeWithRetry` 私有方法本体未改动（重试逻辑只关心 throw，符合"重试返回最后一次成功的 json/headers"语义）；失败响应（最终仍抛出）④ 段不触发、事件不派发——符合语义
- ✅ `calculateBackoff` 未改动

### 3.4 `src/rest-transport.ts`

## 5. 开发过程中发现的问题与处理

1. **RestTransport 现存测试回归**（V1.0.8 实现引入）：`extractEvents` 需读 `response.headers`，而 `rest-transport.test.ts` 既有 mock 响应用例（`mockFetch` / 401 直接 mock / uploadFile）未提供 `headers` 属性 → 运行时 `headers.get` 抛 TypeError。**处理**：`mockFetch` 增加 `headers: new Headers()` 默认参数，401 用例补 `headers: new Headers()`，uploadFile 用例已有 headers 无需改。修复后 24 测试全过。
   - 注：`transport.test.ts` 不受影响（`GraphQLTransport.extractEvents` 不读 headers，签名 `_headers`），36 测试全过。

2. **`parseRpcEventEnvelope` string 分支补充**（实现期修正）：方案 §2.1 代码片段未含 JSON string 输入处理，但 §2.3.4 REST 路径传解码后的字符串、且注释明确"内部 JSON.parse 必须 try/catch 返回 []"。实现已按注释语义补全 string 分支，与方案意图一致。

3. **`Buffer` 类型声明**：仓库无 `@types/node`，`event.ts`/测试内局部 `declare const Buffer` 仅为编译期提供最小类型，运行时为 Node 全局。属性测试文件内局部声明，无污染。
