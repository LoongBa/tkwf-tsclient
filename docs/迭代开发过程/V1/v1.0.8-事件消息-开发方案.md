> **版本**：v1.0.8
> **架构依据**：ADR33（RPC 响应携带事件：领域事件同步传播）、TKW.Framework v4.9.69 方案（侧信道契约）
> **状态**：待审核（已通过 Oracle 审核修订——bg_b8d45ba4：5 项必修 M1-M5 + 3 项建议 S1-S3 已全部纳入）
> **前置**：v1.0.7（QueryBuilder 聚合增强与功能补齐）；服务端 ADR33 阶段 1 已完成（`InvocationContext.CollectedEvents` 侧信道，W10）
> **跨仓库关联**：TKW.Framework ADR33（服务端契约定义）、`@tkwf/tsclient`（本仓库，消费端实现）

---

## 1. 目标

为 ts-client 实现 ADR33 **阶段 3** 的消费端能力：解析服务端 RPC 响应中携带的领域事件并同步派发到本地 Handler。

读者应在 3 句话内明白：`BaseHttpTransport`/`GraphQLTransport`/`RestTransport` 从响应**侧信道**（GraphQL `extensions.tkwf.events` / REST `X-TKWF-Events` 响应头）提取事件载荷；新增 `TkwfEventBus` 事件派发器（`onEvent`/`off`/`emit`）；`DomainHostClient.onEvent()` 注册 Handler，每次响应自动解包并派发。**不破坏现有 `ReturnStyle` 返回契约**——事件走独立侧信道，业务返回值原样透传。

### 服务端契约（本仓库只消费，不实现）

| 传输 | 载体 | 编码 |
|------|------|------|
| GraphQL | `extensions.tkwf.events` | JSON（响应 extensions 字段） |
| REST | HTTP 响应头 `X-TKWF-Events` | Base64(JSON)（兼容无 Base64 的纯 JSON） |

**事件载荷结构**（ADR33 §决策 2，跨进程契约）：

```jsonc
{
  "events": [
    {
      "name": "OrderCreated",            // 事件名（类型去 Event/Eto 后缀 + [EventName]）
      "type": "TKW.MyProject.Events.OrderCreatedEvent", // 完整类型名
      "data": { "orderId": 123 },        // 事件字段（JSON 化）
      "triggeredBy": "u-42",             // 触发者（可选）
      "timestamp": "2026-08-26T12:00:00Z",
      "correlationId": "abc-123"         // 关联 ID（可选）
    }
  ]
}
```

## 2. 设计

### 2.1 新增类型：RpcEventData / RpcEventEnvelope

新增文件 `src/event.ts`，定义跨进程契约类型：

```typescript
/** 单个 RPC 响应携带的领域事件（对齐 ADR33 §决策 2 载荷）。 */
export interface RpcEventData {
  name: string;
  type: string;
  /** 事件字段（JSON 化）。框架侧"事件字段 JSON 化"未限定为对象，用 unknown 保持契约严谨。 */
  data: unknown;
  triggeredBy?: string;
  timestamp: string;
  correlationId?: string;
}

/** RPC 响应事件载荷 envelope。 */
export interface RpcEventEnvelope {
  events: RpcEventData[];
}

/** 事件 Handler：收到匹配事件名时回调。 */
export type EventHandler = (event: RpcEventData) => void;
```

**容错解析**：`parseRpcEventEnvelope(raw: unknown): RpcEventData[]`（放 `src/event.ts`）——**逐条过滤**（对齐框架侧"绝不因单条失败丢弃整个侧信道"语义：非法条目跳过，保留合法条目），整体非法返回 `[]`。内部 `JSON.parse` 必须 try/catch 返回 `[]`。事件是尽力而为的附加，不得阻断业务结果。

```typescript
/** 容错解析：逐条过滤，单条非法跳过，其余保留（对齐框架侧"单条失败不丢整个侧信道"）。 */
export function parseRpcEventEnvelope(raw: unknown): RpcEventData[] {
  const env = raw as { events?: unknown[] };
  if (!env || !Array.isArray(env.events)) return [];
  const out: RpcEventData[] = [];
  for (const item of env.events) {
    const e = item as Record<string, unknown>;
    if (typeof e?.name !== "string" || typeof e?.type !== "string" || typeof e?.timestamp !== "string") {
      continue; // 跳过非法条目
    }
    out.push({
      name: e.name, type: e.type,
      data: e.data ?? {},
      triggeredBy: typeof e.triggeredBy === "string" ? e.triggeredBy : undefined,
      timestamp: e.timestamp,
      correlationId: typeof e.correlationId === "string" ? e.correlationId : undefined,
    });
  }
  return out;
}
```

### 2.2 新增 TkwfEventBus（事件派发器）

同放 `src/event.ts`，进程内事件注册 + 派发（对标 ADR21 本地事件总线语义，但仅服务 RPC 同步事件）：

```typescript
export class TkwfEventBus {
  /** 注册 Handler，返回取消订阅函数。 */
  on(eventName: string, handler: EventHandler): () => void;
  /** 显式注销。 */
  off(eventName: string, handler: EventHandler): void;
  /** 按 name 匹配并派发到已注册 Handler。 */
  emit(event: RpcEventData): void;
  /** 解包 envelope 并逐一 emit（内部供 transport 层调用）。 */
  dispatch(envelope: RpcEventData[]): void;
  /** 清空所有 Handler（dispose 用）。 */
  clear(): void;
}
```

**实现要点**：
- 内部 `Map<string, Set<EventHandler>>` 按事件名索引
- `emit` 对未注册事件名静默 no-op（事件是尽力而为，无 Handler 即丢弃）
- `dispatch` 防御性处理：`events` 为空/非法 → 直接返回
- Handler 抛错**不向外传播**（try/catch 包裹，错误走 `console.error`）——事件派发不得破坏主流程返回值

### 2.3 transport 层：响应侧信道提取

#### 2.3.1 ResponseContext 增加 events 字段

`src/transport.ts` 的 `ResponseContext` 增加可选 `events`：

```typescript
export interface ResponseContext<T = unknown> {
  data: T;
  durationMs: number;
  request: RequestContext;
  /** V1.0.8: RPC 响应携带事件（ADR33 侧信道）。无事件时为 undefined。 */
  events?: RpcEventData[];
}
```

#### 2.3.2 BaseHttpTransport：捕获响应头 + 提取钩子

`src/base-http-transport.ts`：

1. **`executeWithRetry` 返回结构化结果 `{ data, json, headers }`**（Oracle M2，落实 ④ 段可及性）：当前 `executeWithRetry` 闭包内 `const json = JSON.parse(bodyText); return this.parseResponse(json, status)` **只返回 `data`**，`json`（含 GraphQL `extensions`）与 `response.headers`（REST 侧信道）都被闭包吞掉，④ onResponse 段不可达。改造为回调返回结构体，retry 逻辑无需改动（只关心 throw）：

```typescript
// executeHttp 内 ③ 段
const { data, json, headers } = await this.executeWithRetry<{
  data: T; json: unknown; headers: Headers;
}>(async () => {
  let response: Response;
  // ...fetch + 状态校验不变...
  const bodyText = await response.text();
  const json = JSON.parse(bodyText);
  const data = this.parseResponse<T>(json, response.status);
  return { data, json, headers: response.headers };
}, ctx.field);

// ④ onResponse 段
const events = this.extractEvents(json, headers);
if (this.options.onResponse) {
  this.options.onResponse(
    { data: data as T, durationMs, request: ctx, ...(events ? { events } : {}) } satisfies ResponseContext<T>,
    ctx,
  );
}
return data as T;
```

2. **新增受保护方法 `extractEvents`**（基类默认返回 `undefined`，子类 override；用默认方法而非 `?` optional property）：

```typescript
/**
 * V1.0.8: 从响应中提取 RPC 事件载荷（ADR33 侧信道）。
 * @param json    - 已解析的响应 JSON（GraphQL 用 extensions；REST 用不到）
 * @param headers - fetch Response 头（REST 用 X-TKWF-Events）
 * @returns 事件数组；无事件返回 undefined
 */
protected extractEvents(_json: unknown, _headers: Headers): RpcEventData[] | undefined {
  return undefined;
}
```

3. **`executeHttp` 组装 `ResponseContext` 时调用钩子**：见上 ④ 段代码（`const events = this.extractEvents(json, headers);`）。

> **重试语义确认**：`executeWithRetry` 重试时每次重新 fetch，返回**最后一次成功**的 `json`/`headers`——符合预期。若最终仍失败抛错，④ 段 onResponse 不触发，事件不派发——**符合语义**（失败响应不应派发事件）。

#### 2.3.3 GraphQLTransport：extensions 提取

`src/transport.ts` 的 `GraphQLTransport` 覆盖 `extractEvents`：

```typescript
protected extractEvents(json: unknown, _headers: Headers): RpcEventData[] | undefined {
  const extensions = (json as { extensions?: { tkwf?: { events?: RpcEventData[] } } })?.extensions?.tkwf?.events;
  return Array.isArray(extensions) && extensions.length ? extensions : undefined;
}
```

> `parseResponse` 保持不变（仍返回 `data as T`，业务结果原样透传）；extensions 仅经 `extractEvents` 提取，不污染 data。

#### 2.3.4 RestTransport：响应头提取（Base64Url 解码 + 截断处理）

`src/rest-transport.ts` 的 `RestTransport` 覆盖 `extractEvents`：

```typescript
protected extractEvents(_json: unknown, headers: Headers): RpcEventData[] | undefined {
  const raw = headers.get("X-TKWF-Events");
  if (!raw) return undefined;
  // Oracle M3: 截断标记——4KB 预算截断后 payload 是不完整 JSON，尽力解析失败则丢弃（不阻断业务）
  if (headers.get("X-TKWF-Events-Truncated") === "true") {
    console.warn("[tkwf] RPC events truncated (4KB budget), partial parse may fail");
  }
  let decoded: string;
  try { decoded = base64UrlDecode(raw); }   // Oracle M1: 固定 Base64Url 解码
  catch { return undefined; }                // 解码失败 → 丢弃，不阻断业务
  const env = parseRpcEventEnvelope(decoded); // 内部 JSON.parse try/catch → []
  return env.length ? env : undefined;
}
```

**`base64UrlDecode`（Oracle M1，硬伤修订）**：框架侧 REST 侧信道**固定 `Base64Url(UTF-8 JSON)`**，非标准 Base64 双兼容。需三处处理：

```typescript
/** Base64Url(UTF-8 JSON) 解码。框架侧 REST 侧信道固定此编码。 */
function base64UrlDecode(str: string): string {
  // ① Base64Url 字母表 → 标准 Base64（-/_ 替代 +//）
  const b64 = str.replace(/-/g, "+").replace(/_/g, "/");
  // ② 补 padding（Base64Url 通常省略 =）
  const padded = b64 + "=".repeat((4 - (b64.length % 4)) % 4);
  // ③ 跨环境二进制解码 + UTF-8 还原（关键：中文事件名/data 不可损坏）
  const binary =
    typeof atob === "function"
      ? atob(padded)                                        // 浏览器
      : Buffer.from(padded, "base64").toString("binary");   // Node
  const bytes = Uint8Array.from(binary, (c) => c.charCodeAt(0));
  return new TextDecoder("utf-8").decode(bytes);
}
```

> **修订要点**（Oracle M1）：① Base64Url 用 `-`/`_`，标准 `atob`/`Buffer.from(base64)` 对 `-`/`_` 行为依赖实现（Node 静默截断出乱码）；② Base64Url 通常省略 padding，`atob` 缺 padding 部分实现失败；③ `atob` 返回 binary string（1 字符=1 字节），对非 ASCII 必须 `TextDecoder('utf-8')` 还原。**移除**原"兼容 Base64 与纯 JSON"的双兼容设计——框架侧不存在"纯 JSON"路径，`X-TKWF-Events` 恒为 Base64Url。

### 2.4 派发接入：ServiceProxy 或 DomainHostClient

事件最终要派发到业务 Handler。两条候选接入路径，**选定 a**：

- **(a) DomainHostClient 派发（推荐）**：`DomainHostClient` 持有 `TkwfEventBus` 实例；`createTransport()` 构造 transport 时把 `onResponse` 处理器设为内部方法——先调用用户注册的 `onResponse`，再调用 `this.eventBus.dispatch(res.events)`。统一入口、单一事件总线，且覆盖 `Use()`/`QueryBuilder` 所有走 transport 的路径。
- (b) ServiceProxy 内联派发——需在 `ServiceProxyOptions` 注入 eventBus，且 QueryBuilder 的 `executeRawGraphQL` 路径不经 ServiceProxy，会漏。放弃。

**具体改动**（`src/domain-host-client.ts`）：

```typescript
private eventBus: TkwfEventBus;

// 新增公开 API：注册事件 Handler
onEvent(eventName: string, handler: EventHandler): this {
  this.eventBus.on(eventName, handler);
  return this;
}

// 新增公开 API：访问底层总线（高级用法，如批量 on/off/clear）
getEventBus(): TkwfEventBus {
  return this.eventBus;
}
```

**`createTransport()` 内部 onResponse 包装**：

```typescript
private createTransport(): Transport {
  // ...既有逻辑...
  const opts = {
    url: this.endpoint,
    signHandler: this.signHandler,
    onRequest: this.onRequestHandler,
    onResponse: (res: ResponseContext, req: RequestContext) => {
      this.onResponseHandler?.(res, req);        // 用户 interceptor 优先
      if (res.events?.length) this.eventBus.dispatch(res.events);  // V1.0.8 事件派发
    },
    retry: ...,
  };
  // ...
}
```

**`dispose()` 补充**：`this.eventBus.clear()`（释放 Handler 引用）。

### 2.5 DomainClientUser 事件可达性（Oracle M5：误判修正）

**修正（Oracle M5）**：原方案 §2.5/§6.1 判断"`DomainClientUser` 内部创建自己的 transport，user 路径不走 host eventBus"是**误判**。核证 `domain-client-user.ts`：`this.transport = options.transport`——`DomainClientUser` **接收** host 传入的 transport，**不**自建。

实际链路：`GetUser()/GetGuest()`（`domain-host-client.ts`）→ `this.createTransport()`（host 私有方法，本方案 §2.4 改造点）→ transport 传入 `DomainClientUser`。因 §2.4 的 onResponse 包装（含 `eventBus.dispatch`）在 `createTransport` 内，**user 的所有 RPC（login/ping/logout/Call/Use）都会触发 host 的 eventBus 派发**——user 路径**已覆盖**。

**覆盖确认**：
- `Use()`：走 host 的 ServiceProxy → transport ✅
- `QueryBuilder.executeRawGraphQL`：`GraphQLTransport.executeRawGraphQL` → 同一 `executeHttp` → 同 onResponse 包装 ✅
- `GetUser()/GetGuest()` 返回的 user：其 transport 由 host `createTransport()` 创建，经 §2.4 包装 ✅

**真正未覆盖的缺口**（应替换原开放项）：`DomainHostClientOptions.transport` **注入自定义 transport**（`domain-host-client.ts` `if (this.injectedTransport) return this.injectedTransport`）——注入 transport 不经 `createTransport` 包装，无 eventBus 派发。此为 mock/测试场景，可接受（§6.2 mock 侧对齐），但在 §6.1 明确标注"注入 transport 不派发"。

## 6. 向后兼容与开放项

**向后兼容**：
- `ResponseContext.events` 为**可选**字段，无事件响应时为 `undefined`，现有 `onResponse` interceptor 签名不变
- `parseResponse` 返回契约不变（`data` 原样），extensions/header 只经新增 `extractEvents` 钩子消费
- 所有新增 API（`onEvent`/`getEventBus`/`TkwfEventBus`）均为增量，不破坏现有调用
- 现有 220+ 测试应全部通过

**开放项（不在本迭代范围）**：
1. **注入自定义 transport 的事件派发**（Oracle M5 修正）：`DomainHostClientOptions.transport` 注入的 transport 不经 `createTransport` 包装，无 eventBus 派发。此为 mock/测试场景，可接受——mock 侧需自行实现 `extractEvents`（见第 2 项）。host 创建的所有 transport（含 `GetUser()`/`GetGuest()` 的 user）**均已覆盖**。
2. **`@tkwf/tsclient-mock` 支持**：mock transport 需实现 `extractEvents` 以支持事件场景测试——独立于本仓库，留待 mock 侧对齐。
3. **与 tkwf-tsclient SDK 端到端集成测试**：需真实服务端（SG Decorator 序列化 + 侧信道）配合，作为后续集成验证，非本仓库单测范畴。
4. **事件 Handler 的异步支持**：当前 `EventHandler` 为同步 `void`；若需 `Promise` 支持（await 派发），列为未来增强，本迭代不引入。
