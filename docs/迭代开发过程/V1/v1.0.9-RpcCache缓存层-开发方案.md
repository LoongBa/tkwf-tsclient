# v1.0.9 — RpcCache 缓存层：借鉴 TanStack Query-core（可选懒加载 + 子路径导出）

> **版本**：v1.0.9
> **架构依据**：TanStack Query v5 分层架构（`@tanstack/query-core` 框架无关核心）、Discussion #10735（库作者 build on query-core 模式）、TanStack Issue #4885（避免 core 双实例）
> **状态**：待复审（已通过 Oracle 审核修订——bg_b4833841：5 项必修 M1-M5 + 8 项建议 S1-S8；S1/S2/S3/S4/S6/S7/S8 已纳入，S5 明确放弃）
> **前置**：v1.0.8（RPC 事件侧信道）；v1.0.6（graphql optional peerDependency 论证先例）
> **跨仓库关联**：TKW.Framework（RPC 契约）、DMP-Lite（React 消费端，QueryBuilder 模板）

---

## 1. 目标

为 ts-client 提供**可选的 RPC 响应缓存能力**：借鉴 TanStack Query 的框架无关核心 `@tanstack/query-core`（缓存/去重/SWR/失效），以 **optional peerDependency + 懒加载** 形态接入——SDK 核心保持零静态依赖，不安装 query-core 时行为与现在完全一致，安装后通过 `@tkwf/tsclient/cache` 子路径获得缓存 API。

读者应在 3 句话内明白：SDK 不实现缓存逻辑、不内置观察者/状态机，只导出 **queryKey 派生 + queryFn 适配 + `enableRpcCache()` 懒加载工厂**（内部 `await import("@tanstack/query-core")`，复用 v1.0.6 graphql 的动态 import 模板）；消费端（React/Vue/vanilla）把 SDK 的 `queryKey`/`queryFn` 接入 `@tanstack/react-query`/`vue-query` 或直接用 `QueryClient` 命令式 API；未安装 query-core 时抛清晰引导错误，不静默降级。

**设计边界（借鉴不照搬）**：不引入观察者/订阅原语进核心（框架耦合，留给框架适配层）；不做乐观更新（应用层关注）；不做离线持久化；不做 infinite queries（QueryBuilder 游标分页已覆盖）。事件侧信道（v1.0.8）保持"真实请求后派发"，缓存命中不重放。

---

## 2. 设计

### 2.1 依赖形态：optional peerDependency（修正 v1.0.6 未落地问题）

**背景**：v1.0.6 方案要求给 `graphql` 加 optional peerDependency（`peerDependencies` + `peerDependenciesMeta.optional: true`），但实际落地只有 `devDependencies`（审核报告误报"✓ 已实现"）。本迭代**真正落地**该机制，并同步给 `graphql` 补上。

`package.json` 变更：

```jsonc
{
  "peerDependencies": {
    "@tanstack/query-core": "^5.0.0",
    "graphql": "^16.0.0 || ^17.0.0"
  },
  "peerDependenciesMeta": {
    "@tanstack/query-core": { "optional": true },
    "graphql": { "optional": true }
  },
  "devDependencies": {
    "@tanstack/query-core": "5.102.8",   // 测试锁定具体版本
    "graphql": "^17.0.2"
  }
}
```

> **修订说明（Oracle M3）**：原方案 peerDep `graphql: ^16.0.0` 与 devDep/当前实际 `^17.0.2` 冲突。npm 7+ 对 optional peerDep 虽不自动安装，但**消费端已装 graphql@17 时会做版本兼容检查并 emit warning**（`^16.0.0` 不含 17.x）。修订为 OR 范围 `^16.0.0 || ^17.0.0`（`parseGraphQLSchema` 仅用 `graphql.parse()`，16/17 均稳定）。

**关键事实依据**（npm registry 实证）：
- `@tanstack/query-core` 是独立包，`dependencies: {}`、`peerDependencies: {}`、**零依赖、无 React**、`sideEffects: false`、双格式（ESM+CJS）
- `@tanstack/react-query` 以**精确版本**锁定 query-core 为 dependency → 消费端装 react-query 时 query-core 已在 node_modules，**SDK 缓存功能对 React 用户零新增安装**
- 不存在 `@tanstack/query` 全家桶包；官方明确支持库作者只依赖 query-core（TkDodo, Discussion #4771）

**版本策略**：peerDependencies 用 `^5.0.0` 宽松下限（消费方 `npm update` 自主升级，SDK 不被上游发版绑架）；devDependencies 锁定 `5.102.8` 保证测试可复现。

### 2.2 exports 子路径：`@tkwf/tsclient/cache`

利用现有构建配置（`tsconfig.build.json` 已 `include: ["src"]` + `rootDir: "src"`），新增源文件 `src/cache.ts` 自动产出 `dist/cache.js` + `.d.ts`，只需在 `exports` 加一条子路径：

```jsonc
"exports": {
  ".": { "types": "./dist/index.d.ts", "import": "./dist/index.js" },
  "./src": { "types": "./src/index.ts", "import": "./src/index.ts" },
  "./cache": { "types": "./dist/cache.d.ts", "import": "./dist/cache.js" }
}
```

**不建独立子包**（`@tkwf/tsclient-query`）：当前仓库无 workspaces/monorepo 配置，独立子包需新建目录 + 独立 package.json + 独立构建/发布流水线，改造成本最高。子路径是单包结构下最低成本方案，且 `files: ["dist"]` 已自动包含 `dist/cache.js`。

### 2.3 新增模块 `src/cache.ts`（懒加载工厂 + 适配器）

复用 v1.0.6 `src/codegen/schema-parser.ts:244-252` 的动态 import + 引导错误模板（`verbatimModuleSyntax` 已启用，用 `typeof import(...)`）：

```typescript
import type { Transport } from "./transport";

// ── 类型（零运行时，静态引用，不加载 query-core）──
export interface RpcCacheConfig {
  /** staleTime 默认值（毫秒）。query-core 语义：期限内不重新请求。默认 0 = 重取 + 去重兜底。 */
  staleTime?: number;
  /** gcTime 默认值（毫秒）。query-core 语义：无观察者后保留时长。 */
  gcTime?: number;
}

export type RpcQueryKey = readonly [
  scenario: string,
  sessionKey: string | null,
  field: string,
  variables: unknown,
  selection?: string,
];

/**
 * 传给 queryFn 的上下文。对齐 TanStack QueryFunctionContext 的可用字段子集——
 * 只暴露 signal（TanStack 保证注入），不声明 TanStack 不提供的幻影字段。
 * 修订说明（Oracle M1）：原 RpcQueryContext<T> 含必填 fetcher 与 variableTypes，
 * TanStack QueryFunctionContext 无此二字段，strictFunctionTypes 下消费端赋给
 * useQuery({ queryFn }) 逆变检查失败不可编译；createRpcQueryFn 也从未使用 ctx.fetcher。
 */
export interface RpcQueryContext {
  signal?: AbortSignal;
}

export interface RpcQueryOptions<T> {
  scenario: string;
  field: string;
  type?: "query" | "mutation";
  variables?: Record<string, unknown>;
  variableTypes?: Record<string, string>;
  selection?: string;
  transport: Transport;
  getSessionKey: () => string | null;
}

// ── queryKey 派生（框架无关、零依赖、确定性序列化，对齐 TanStack hashKey 语义）──
export function createRpcQueryKey(
  scenario: string,
  sessionKey: string | null,
  field: string,
  variables?: Record<string, unknown>,
  selection?: string,
): RpcQueryKey {
  return [scenario, sessionKey, field, stableSerialize(variables), selection] as const;
}

// ── queryFn 适配：把 tsclient Transport 调用包装成 TanStack queryFn 形态 ──
// 修订说明（Oracle M1）：ctx 参数类型为无泛型 RpcQueryContext（只含 signal），
// 与 QueryFunctionContext 结构兼容，strictFunctionTypes 通过。
export function createRpcQueryFn<T>(
  options: RpcQueryOptions<T>,
): (ctx: RpcQueryContext) => Promise<T> {
  const { transport, field, type = "query", variables, variableTypes, selection, getSessionKey } = options;
  return (ctx) =>
    transport.execute<T>({
      field,
      type,
      variables,
      variableTypes,
      selection,
      sessionKey: getSessionKey() ?? undefined,
      signal: ctx.signal,
    });
}

// ── 懒加载工厂（复用 schema-parser 模板；Oracle M4：webpackIgnore + 变量模块名）──
const QUERY_CORE_MODULE = "@tanstack/query-core";

export interface RpcCacheClient<T = unknown> {
  /** QueryClient 实例。修订说明（Oracle S1）：泛型 T 由调用点指定（如 enableRpcCache<QueryClient>()），
   * 消除消费端 as 收窄；未装 query-core 时 T 退化为 unknown，.d.ts 无 query-core 类型引用不炸。 */
  getQueryClient(): T;
  /** 登出/切换会话时清理该会话全部缓存。修订说明（Oracle S2/S3）：先 cancelQueries 再 removeQueries
   * 防 in-flight 竞态；sessionKey 接受 null（guest 查询）。 */
  clearSession(scenario: string, sessionKey: string | null): void;
}

export async function enableRpcCache<T = unknown>(config?: RpcCacheConfig): Promise<RpcCacheClient<T>> {
  let queryCore: typeof import("@tanstack/query-core");
  try {
    // Oracle M4: webpackIgnore 防止 Webpack 5 静态分析尝试解析可选依赖（未装时 build 失败）；
    // 变量模块名绕过 Vite 静态分析。Vite 侧另需消费端 optimizeDeps.exclude（见 §6 与 README）。
    queryCore = await import(/* webpackIgnore: true */ QUERY_CORE_MODULE);
  } catch {
    throw new Error(
      'The "@tanstack/query-core" package is required for the RPC cache. Install it: npm install @tanstack/query-core',
    );
  }
  const { QueryClient } = queryCore;
  const client = new QueryClient({
    defaultOptions: {
      // Oracle M2（最关键必修项）：queries 必须显式 retry:false —— TanStack 默认 query retry=3，
      // 若省略则 transport 重试 3 次抛错后 TanStack 再重试 3 次（每次又触发 transport 重试），
      // 最坏 12 次尝试，违反 Q6 单一重试归属。
      queries: { staleTime: config?.staleTime ?? 0, gcTime: config?.gcTime, retry: false },
      mutations: { retry: false },
    },
  });
  return {
    getQueryClient: () => client as T,
    // Oracle S4：参数名用 scenario（非 _scenario，避免下划线误导）
    clearSession: (scenario, sessionKey) => {
      const prefix = [scenario, sessionKey] as const;
      // Oracle S2：先 cancel 再 remove，防登出时 in-flight 请求写完已清除的 key
      client.cancelQueries({ queryKey: prefix });
      client.removeQueries({ queryKey: prefix });
    },
  };
}

// ── 确定性序列化（对齐 TanStack hashKey：对象 key 排序、undefined 剥离、非 JSON-able 走原样）──
// 修订说明（Oracle S6）：RPC variables 必须 JSON 可序列化（transport 层会因不可序列化而报错），
// 循环引用不在支持范围内；对函数值原样返回（typeof fn !== "object" 分支）。
function stableSerialize(value: unknown): unknown {
  if (value === undefined) return undefined;
  if (value === null || typeof value !== "object") return value;
  if (Array.isArray(value)) return value.map(stableSerialize);
  const out: Record<string, unknown> = {};
  for (const k of Object.keys(value as Record<string, unknown>).sort()) {
    const v = (value as Record<string, unknown>)[k];
    if (v !== undefined) out[k] = stableSerialize(v);
  }
  return out;
}
```

**设计要点（含 Oracle 修订落地）**：
- **M1**：`RpcQueryContext` 只保留 `signal?`，删除 `fetcher`/`variableTypes` 幻影字段；`createRpcQueryFn` 改为单 options 对象入参（`RpcQueryOptions<T>`），`ctx` 参数无泛型——与 TanStack `QueryFunctionContext` 结构兼容，`strictFunctionTypes` 编译通过
- **M2**：`queries.defaultOptions` 显式 `retry: false`——单一重试归属，杜绝双重重试风暴
- **M4**：`/* webpackIgnore: true */` + 变量模块名 `QUERY_CORE_MODULE`——Webpack 5 静态分析不尝试解析可选依赖，未装 query-core 时 `import("@tkwf/tsclient/cache")` 不炸
- **S1**：`RpcCacheClient<T>` 泛型 + `enableRpcCache<T>()`——消费端 `enableRpcCache<QueryClient>()` 后 `getQueryClient()` 直接返回 `QueryClient`，无需 `as`
- **S2/S3/S4**：`clearSession` 先 `cancelQueries` 再 `removeQueries`（防竞态）；`sessionKey: string | null`（guest 可清）；参数名 `scenario`
- `getQueryClient()` 返回 `T`（SDK 自身零 `as any`，`client as T` 是泛型断言）

### 2.4 缓存 key 设计：会话分桶（Oracle Q3 裁决）

queryKey 结构 `[scenario, sessionKey, field, variables, selection]`：

| 维度 | 作用 |
|------|------|
| `scenario` | Tkwf 多场景隔离（`merchant-a` 等） |
| `sessionKey` | **认证隔离**：不同登录会话数据不串（TanStack 无此维度，key 由应用层管；tsclient 必须纳入） |
| `field` | GraphQL field / REST 端点 |
| `variables`（stableSerialize 后） | 请求参数 |
| `selection` | GraphQL 子字段选择（HotChocolate 必须） |

**会话清理三触发点**（对齐 Oracle Watch-out）：登出（`logout()`）、AUTH_EXPIRED 响应、主动 `clearSession()`。`clearSession(scenario, sessionKey)` 用 TanStack partial match（前缀匹配，Oracle 确认语义）清空 `[scenario, sessionKey, ...]` 全部条目，先 `cancelQueries` 再 `removeQueries` 防 in-flight 竞态。SDK 内部不改 `logout()` 行为（保持核心零 query-core 依赖），由消费端在登出流程调用（README 醒目提示，Oracle S8）。

### 2.5 事件侧信道语义（Oracle Q4 + M5 修订）

- v1.0.8 的 RPC 事件（GraphQL `extensions.tkwf.events` / REST `X-TKWF-Events`）在 **transport 层真实请求后派发**
- 缓存命中不产生真实请求 → **不重放事件**——符合"事件是已发生的一次性领域信号"语义
- **修订说明（Oracle M5）**：删除原"queryFn 适配层在结果携带事件时跳过缓存写入"表述——(1) `createRpcQueryFn` 不实现事件检测（直接返回 transport 结果）；(2) TanStack queryFn 返回 data 后**自动缓存**，无"返回数据但不写缓存"的干净 API。带事件响应的 data 会被正常缓存。消费端如需对带事件响应禁用缓存：在 TanStack 侧配 `gcTime: 0` / `staleTime: Infinity` + 手动 `invalidateQueries`，或在 queryFn 内判断后自行处理。文档明确此语义（§6 开放项 #4 同步对齐）。

### 2.6 双重重试协调（Oracle Q6 裁决）

| 层 | 重试策略 | 说明 |
|----|---------|------|
| transport（现有） | `retryOn: [NETWORK_ERROR, SERVER_ERROR]`，指数退避 + jitter | **默认重试归属**，保留 |
| query-core 缓存层 | `retry: false`（本方案默认） | 缓存层不重试，只存成功结果 |
| TanStack 消费端 hooks | 如需接管 → transport 配 `retryOn: []` 或 `maxAttempts: 1`，TanStack 侧设 retry | 文档化二选一，避免双重重试 |

**前置依赖**：`BaseHttpTransport` 已支持 `retryOn: []`/`maxAttempts: 1` 等效关闭（transport.ts:41-47 + base-http-transport.ts:25 默认值），无需改代码。README 文档化协调原则。

### 2.7 死代码修复（Oracle Q7 裁决）

`src/domain-host-client.ts:98` 的 `abortController?: AbortController` 字段**声明但从未实例化**，`dispose()` 实际取消不了请求（探索实证）。处理：**移除死字段** + `dispose()` 文档说明"best-effort，进行中请求依赖 transport signal 链路取消"。不引入新的取消机制（那需要正确实例化 + 接入 transport signal，属另一轮）。

### 2.8 消费端接入形态（不在核心实现，README 提供示例）

```tsx
// React 消费端（README 示例，非 SDK 代码）
import { useQuery } from "@tanstack/react-query";
import { Tkwf } from "@tkwf/tsclient";
import { createRpcQueryKey, createRpcQueryFn, enableRpcCache } from "@tkwf/tsclient/cache";
import type { QueryClient } from "@tanstack/query-core";

// S1：泛型在调用点收窄，无需 as
const cache = await enableRpcCache<QueryClient>();
const client = cache.getQueryClient();

const queryFn = createRpcQueryFn({
  scenario: "default", field: "getOrders", type: "query",
  variables: { page: 1 }, selection: "id,name",
  transport: Tkwf.User.getTransport(), getSessionKey: () => Tkwf.User.sessionKey,
});
const queryKey = createRpcQueryKey("default", Tkwf.User.sessionKey, "getOrders", { page: 1 }, "id,name");

const { data } = useQuery({ queryKey, queryFn, queryClient: client });
```

**Vite 兼容性**（svelte-query 已验证坑，Vite Issue #6007）：可选依赖动态 import 在 Vite dev 模式可能报 `Failed to resolve import`。README 记录消费端配置 `optimizeDeps.exclude: ["@tanstack/query-core"]`；SDK 侧用 `/* webpackIgnore: true */` + 变量模块名写法（见 §2.3 实施注意）兼容 Webpack。

## 6. 向后兼容与开放项

**向后兼容**：
- 主入口 `@tkwf/tsclient` **零新增导出**，核心保持零静态依赖
- 不安装 query-core 的消费端：行为与 v1.0.8 完全一致（缓存功能不可用但无任何报错/警告）
- `./cache` 是**新增子路径**，不影响现有 `"."` / `"./src"` 导出
- transport/ServiceProxy/QueryBuilder 全部不动
- 现有 283 条测试应全部通过

**开放项（不在本迭代范围）**：
1. **官方框架适配包**（`@tkwf/tsclient-react` / `@tkwf/tsclient-vue`）：本迭代只提供框架无关的 queryKey/queryFn 工厂 + README 接入示例；React/Vue 消费端用官方 `@tanstack/react-query`/`vue-query` 直接接入。等真实多框架消费端需求出现再评估官方适配包。
2. **缓存状态订阅原语**（观察者）：不引入。核心只暴露 Promise API；Vue 消费端响应式需求在适配包层解决。
3. **乐观更新 / 离线持久化 / infinite queries**：明确不做（应用层/大表面/已有 QueryBuilder 覆盖）。
4. **带事件响应的缓存策略**：文档化语义（§2.5 M5 修订后：带事件 data 正常缓存，消费端侧用 `gcTime:0`/`staleTime:Infinity`+invalidate 处理），SDK 级自动跳过留待有真实需求时评估。
5. **注入自定义 transport 的事件派发**（v1.0.8 遗留）：mock/测试场景，可接受。
6. **graphql 的 peerDependenciesMeta 落地**：本迭代补上（§2.1），但其运行时行为（schema-parser）不变。
7. **`createRpcQuery()` 便利工厂（Oracle S5，明确放弃）**：合并 queryKey/queryFn 生成防变量分叉。本迭代保留独立 `createRpcQueryKey` + `createRpcQueryFn`，README 已示范正确用法（同源 variables 两处调用）；S5 留待下迭代评估（若消费端反馈 key/fn 分叉 bug 频发）。
8. **`enableRpcCache()` 单例/调用时机**：README 明确"应在应用入口调用一次"（每次调用新建 QueryClient，组件内调用会创建独立缓存）；不提供 getOrCreate 单例变体，保持最小 API 面。
