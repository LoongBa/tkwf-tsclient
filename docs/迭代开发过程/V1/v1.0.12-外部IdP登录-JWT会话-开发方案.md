## 1. 缺口背景与设计原则对照

### 1.1 缺口根因（已逐条源码核实）

| # | 断言 | 核实结果 | 源码/契约证据 |
|---|------|---------|--------------|
| 1 | **SDK 无外部 IdP 登录 API** | ✅ | `src/domain-client-user.ts` 登录族仅 `loginAs`/`loginBySms`/`loginByContext`/`loginSecure`/`registerSecure`/`logout`/`ping`（L161-403）；`EXPLICIT_MUTATIONS`（L507-514）仅登录 6 项——**无任何 channelType/城邦/微信/ticket 概念** |
| 2 | **SDK 会话模型只认 `sessionKey`，丢弃 JWT** | ✅ | `LoginPayload` 有 `accessToken/refreshToken/expiresAt` 字段（L8-17）但 `persist()` 仅存 `sessionKey/userName/displayName`（L141-154）；`restore()` 仅凭 `state.sessionKey` 判认证（L122-138）——**JWT 拿到即弃，无法代表外部 IdP 登录后的会话**（注意：GraphQL 登录族 loginByPassword/loginBySms/loginByContext 的 selection 均已请求 JWT 三件，服务端一直有返，SDK 一直丢弃——"拿到即弃"是全登录路径现状） |
| 3 | **服务端外部登录产物是 JWT，非 sessionKey** | ✅ | AuthCenter `login/external/{channelType}` 返回 `TokenResponse`（`AuthCenterWebExtension.cs:380`，`record TokenResponse(string AccessToken, string RefreshToken, string TokenType, int ExpiresIn)`）——RS256 JWT + service 端 refresh rotation 落库，**与 SDK `sessionKey`（GraphQL 会话）模型不同源** |
| 4 | **外部登录成功后无会话承载** | ⚠️ 推论 | 即使前端拿 code 直调 `login/external` 成功拿到 JWT，SDK 无字段持久化、无 Bearer 携带、无 refresh 续期——下个请求 401 |
| 5 | **缺 OAuth 发起/回调辅助** | ✅ | SDK 无"构造微信 authorize URL / 解析回调 code/state"工具（全仓零命中 openid/authorize/redirect_uri/state 相关 API）；`QueryString`（query-string.ts）是通用工具，覆盖 OAuth 回调解析能力但无预设 |

### 1.2 设计原则对照

| TKWF 原则 | 现状问题 | **本方案对齐** |
|---|---|---|
| **P5 显式决策优于自动行为** | 前端只能裸 fetch 外部端点（绕过 SDK 传输/错误归一化/会话持久化）或手拼 sessionKey（伪造会话，错误模型全错） | 新增**显式方法** `loginByExternal(channelType, parameters)`（Guest 语义）；`restore()` 显式区分 sessionKey 会话 / externalSession（JWT）会话两形态 |
| **P2 唯一权威事实源，下游纯消费** | 服务端 JWT 契约（TokenResponse）已冻结，SDK 另存 sessionKey 会话 = 两套会话源 | SDK 会话模型为**两形态独立并存**（README 文档化）：GraphQL 登录 → sessionKey；外部 IdP → `externalSession`（独立字段，形态即字段存在性，零 flag 判别）；两者互不隐式转换 |
| **P7 缺省=守卫硬失败，不静默失效** | JWT 拿到即弃 = 静默丢会话 | `loginByExternal` 前置守卫（channelType 非空/code 存在）+ 响应缺 AccessToken → 显式错误（`INVALID_ARGUMENT`/`EXTERNAL_LOGIN_FAILED`/`JWT_SESSION_INVALID`），不静默成功 |
| **P8 领域自治与框架管理边界** | 认证是 Guest 行为（服务端端点 `.AllowAnonymous()` 游客帧） | `loginByExternal` 挂 **Guest** 语义（`GetGuest()` 实例方法），登录成功后 `restore()` 支持 externalSession 恢复；OAuth 平台知识（scope/snsapi_base 等）**不进 SDK**（归服务端/消费端） |
| 元原则（先例可能错） | 不能因"现有登录都是 sessionKey"否定 JWT 会话；不能因"现有 transport.execute 是 GraphQL 形态"否定专用 REST 登录通道 | 以对接认证中心为判据：JWT 是服务端冻结契约，SDK 支持独立 externalSession 形态 |

## 2. 设计

### 2.0 关键 wire 契约事实（已对服务端源码实证，方案设计前提）

> 本迭代所有 URL/字段/错误码设计以上述实证为准，**不以服务端 record 自身 XML 注释为准**（服务端 XML doc 声称 snake_case，实际 wire 为 camelCase）：
>
> 1. **TokenResponse wire casing = camelCase**：`AuthCenterWebExtension.cs:380` record 无 `[JsonPropertyName]` → wire keys 为 `accessToken`/`refreshToken`/`tokenType`/`expiresIn`；`Results.Ok` 默认 camelCase（同文件 :413 VerifyResponse 局部显式 `[JsonPropertyName("auth_level")]` 反证默认）。
> 2. **RefreshRequest body casing = camelCase**：`record RefreshRequest(string RefreshToken)`（:395）无 `[JsonPropertyName]` → body key 为 `refreshToken`。
> 3. **端点路由**：`POST {prefix}/login/external/{channelType}`（:89，`.AllowAnonymous()`，游客帧）；`POST {prefix}/refresh`（:93，`.AllowAnonymous()`）；AuthCenter RoutePrefix 默认 `/api/auth`（`AuthCenterEndpointOptions.cs:20`）。
> 4. **channelType 无限定枚举**：服务端仅非空校验 + `parameters["code"]` 必填（:191-194），未知通道 fail-closed（域层 `EnabledAuthTypes`，默认 `["sms","password","federated"]`）。
> 5. **Federation authorize 端点**：`authorize_url`/`state` 来自 `POST /feberation/authorize/start`（`FederationWebExtension.cs:266-274`，匿名对象 `new { authorize_url, state }`——此处真 snake_case）；OAuth 回调为 `GET /feberation/{platformId}/oauth[/{channelId}]/callback` → 302 Redirect；Federation RoutePrefix 默认 `/feberation`（服务端拼写如此，消费方须按此拼写）。

### 2.1 数据流（单通道，对齐 operationKinds v1.0.11 纯消费先例）

```
前端（SPA/微信内浏览器）
  ├─ 静默认证（snsapi_base）：
  │    消费端调 Federation POST /feberation/authorize/start（服务端权威 authorize_url+state；本迭代不封装，见开放项 4）
  │    微信静默回调 → redirectUri?code=...&state=... → resolveOAuthCallback(location)（QueryString 预设）
  │    → guest.loginByExternal("wechat_oauth", { code, channel_id, state }) → 落 externalSession
  ├─ 事件取 OpenId（ticket 落地页）：
  │    微信事件 → 服务端验签取 openid 建映射 → 签 SealedTicket → 图文链接（落地页 URL）
  │    → 落地页 URL 携 ticket → guest.loginByExternal("ticket", { ticket })（扩展侧 v0.10.0 端点配套）
  └─ 会话恢复：Tkwf.User.restore() → 识别 externalSession → 携带 Bearer → 401 → refreshJwt() 显式续期 / onUnauthorized 兜底

SDK 侧新增三件（本迭代）：
  ① REST 登录专用通道：RestTransport.loginByExternal(channelType, parameters) → POST {endpoint}{urlMap["loginByExternal"]}/login/external/{channelType}（{channelType} 经 encodeURIComponent 注入）
  ② 独立 JWT 会话模型：externalSession{accessToken/refreshToken/expiresAt(unix ms)} 持久化 + restore() 两形态 + refreshJwt() 显式续期
  ③ OAuth 回调解析预设：resolveOAuthCallback(url)（QueryString.parse 预设，不新增解析双源；不做 URL 构造——M2/M5）
```

### 2.2 `loginByExternal(channelType, parameters)`（核心 API，Guest 语义）

```typescript
/**
 * V1.0.12：外部 IdP 登录——对接认证中心 `POST {base}{urlMap["loginByExternal"]}/login/external/{channelType}`
 *（服务端契约冻结：body=参数字典透传桥接，返回 TokenResponse JSON，wire 字段 camelCase）。
 *
 * - channelType：自由字符串（wechat_oauth / qq_oauth / alipay_oauth / oidc…，+ 扩展侧 ticket 变体），无客户端枚举
 * - parameters：原样透传（含 code/channel_id/state/ticket 等平台协议字段）
 * - 通道：RestTransport 专用方法（URL 经既有 urlMap 单一解析，channelType encodeURIComponent 注入 path）
 *   ——不经 ServiceProxy 前缀启发式/isMutation（P1 编译期确定路径）
 * - 成功 → 落 externalSession（accessToken/refreshToken/expiresAt 持久化）
 * - 失败 → 抛 DomainClientError（ErrorCode 归一化，见 §2.5）
 */
async loginByExternal(
  channelType: string,
  parameters: Record<string, string>,
  options?: { signal?: AbortSignal },
): Promise<ExternalLoginResult>
```

- **入口归属**：`DomainClientUser` 实例方法（`Tkwf.Guest.loginByExternal(...)` / `host.GetGuest().loginByExternal(...)`）——游客语义，登录成功后会话升级（persist）。
- **REST 专用通道（M3 整改 + N1 配置规约）**：
  - `Transport` 接口新增**可选能力方法** `loginByExternal?(input): Promise<ExternalLoginResult>` 与 `refreshToken?(input): Promise<ExternalLoginResult>`（P3 能力即注册，null 即不支持）——`RestTransport` 实现；`GraphQLTransport` 不注册（refresh 独立方法理由：endpoint/body/错误语义均与 loginByExternal 不同，M7 错误分层要求各自归一）。
  - `RestTransport.loginByExternal` URL 解析 = **urlMap 单一解析机制**（M3：不新增第二套 URL 解析），经 urlMap 模板扩展支持 `{param}` 替换（N4：该模板替换是 urlMap 的新扩展；既有 urlMap 纯字符串值行为不变，向后兼容）：
    `path = urlMap?.["loginByExternal"] ?? "/api/auth/login/external/{channelType}"`（内置默认值对齐 AuthCenter RoutePrefix 默认 `/api/auth`；消费方按实际 RoutePrefix 经 `restUrlMap["loginByExternal"]` 覆盖）
    `url = this.options.url + path`，其中 `{channelType}` 段用 `encodeURIComponent(channelType)` 替换（**S2**，防未来 OIDC channelType 含 `/`/`+` 路径错配；同时仍保留非空前置守卫）。
  - **GraphQL 主传输下的 REST 通道**（N1 配置规约，方案 A：注入式）：`DomainHostClientOptions` 新增 `externalLoginTransport?: Transport`（注入式，与既有 `transport?: Transport` 同模式——mock 注入先例）。消费方在 GraphQL 主传输下如需外部 IdP 登录，构造并注入一个 RestTransport 实例（例如 `new RestTransport({ url: authCenterBaseUrl, pathPrefix: "/api/auth", urlMap: { loginByExternal: "/login/external/{channelType}", refreshToken: "/refresh" } })`）。REST 通道经 `DomainHostClient` 透传给 DomainClientUser；`loginByExternal`/`refreshJwt` 优先用 `externalLoginTransport`，未注入时回退主 transport 的 `loginByExternal?`/`refreshToken?` 能力。若两者皆无 → 守卫抛 `EXTERNAL_LOGIN_FAILED`（"外部 IdP 登录需要注入 externalLoginTransport 或使用 REST 主传输"）——不静默（P7）。REST 通道**不自动继承**主 transport 的 signHandler/retry/onRequest/onResponse——消费方注入时按需自行配置（P5 显式；避免跨实例隐式钩子耦合）。
  - **Config 面（M3：删 `externalLoginEndpoint`）**：`DomainHostClientOptions` **不新增** `externalLoginEndpoint`；URL path 唯一配置点 = 既有 `restUrlMap["loginByExternal"]`/`restUrlMap["refreshToken"]`；REST 通道注入唯一配置点 = `externalLoginTransport`。`tkwf.ts` 经 `extends DomainHostClientOptions` 自动继承 `externalLoginTransport`（无新增代码）。
- **`ExternalLoginResult` 类型（M4/M11 + N2）**：独立于 `LoginPayload`，与服务端 TokenResponse wire 1:1 映射（下游纯消费，P2）——**严格 4 字段，不含 userName/displayName**（服务端 TokenResponse 无此二字段；JWT claims 亦无显示名，provenance 不明——N2）：
  ```typescript
  export interface ExternalLoginResult {
    accessToken: string;
    refreshToken: string;
    tokenType: string;   // "Bearer"
    expiresIn: number;   // 秒（服务端 ExpiresIn int）
  }
  ```
  `LoginPayload` 保持原貌不变（GraphQL 登录族响应形状；其 `accessToken?/refreshToken?/expiresAt?` 字段不扩展、不外接 JWT 会话）。JWT 会话的 userName/displayName **存 null**（消费方按需另调 profile API 补全，不归 SDK——N2）。

### 2.3 JWT 会话模型（externalSession，M4/M7/M8/M11 整改）

```typescript
// DomainClientUser 新增（V1.0.12）——独立字段，与 sessionKey 并列，零 flag 判别
externalSession: { accessToken: string; refreshToken: string; expiresAt: number } | null = null;
// expiresAt = unix 毫秒（SDK 计算 Date.now() + expiresIn * 1000；与服务端 GraphQL expiresAt ISO 字符串不同源——M11）

// persist() 扩展（向后兼容：既有 sessionKey 会话持久化格式不变，仅增量追加 externalSession 键；M4）
private persist(): void {
  if (this.sessionKey || this.externalSession) {
    this.storage.setItem(this.storageKey, JSON.stringify({
      sessionKey: this.sessionKey,
      userName: this.userName,
      displayName: this.displayName,
      externalSession: this.externalSession,   // { accessToken, refreshToken, expiresAt } | null
    }));
  } else {
    this.storage.removeItem(this.storageKey);
  }
}

// restore() 扩展：形态即字段存在性（零 flag 判别）
restore(): boolean {
  const raw = this.storage.getItem(this.storageKey);
  if (!raw) return false;
  const state = JSON.parse(raw);
  if (state.sessionKey) {
    this.sessionKey = state.sessionKey;
    this.isAuthenticated = true;
    this.userName = state.userName ?? null;
    this.displayName = state.displayName ?? null;
    return true;                                     // GraphQL 会话（既有路径不变）
  }
  if (state.externalSession?.accessToken) {
    this.externalSession = state.externalSession;    // { accessToken, refreshToken, expiresAt }
    this.isAuthenticated = true;
    this.userName = null;                            // N2：JWT 会话无 userName/displayName（wire 无此字段）
    this.displayName = null;
    return true;                                     // JWT 会话（新形态）
  }
  return false;
}
```

- **形态切换互斥不变量（N3）**：运行时不变量——`sessionKey` 与 `externalSession` **至多一个非 null**（持久化 JSON 两键并存可行，但互斥保证 restore 不被遮蔽）：
  - `loginByExternal` 成功 → `this.sessionKey = null; this.externalSession = { accessToken, refreshToken, expiresAt }; this.persist()`（清旧 GraphQL 会话，防 sessionKey 优先分支遮蔽 JWT 会话）
  - `loginAs`/`loginBySms`/`loginByContext` 成功 → `this.externalSession = null; this.sessionKey = payload.sessionKey ?? null; this.persist()`（清旧 JWT 会话，防 externalSession 残留）
  - `restore()` 分支顺序维持 sessionKey 优先（既有行为零回归）；互斥不变量保证不会出现双形态并存被误判。
- **clearLocalState() 同步清理（M4 配套）**：`logout()`/`clearLocalState()`（domain-client-user.ts:405-411）除 sessionKey 外，必须同时置空 `externalSession`——防止登出后内存残留 JWT 字段、后续 persist() 重写陈旧会话。
- **传输携带（M6 整改）**：JWT 会话下请求并发 `Authorization: Bearer <accessToken>`。**注入点 = 4 处子类方法**（非 BaseHttpTransport 抽象类——BaseHttpTransport 只提供 executeHttp 生命周期，不构造协议头）：
  | # | 注入点 | 位置 | 变更 |
  |---|--------|------|------|
  | 1 | `GraphQLTransport.execute` | `transport.ts:106` | `if (bearerToken) headers["Authorization"] = "Bearer " + bearerToken` |
  | 2 | `GraphQLTransport.executeRawGraphQL` | `transport.ts:149` | 同上（签名尾参追加 `bearerToken?`，源兼容） |
  | 3 | `RestTransport.execute` | `rest-transport.ts:117` | 同上 |
  | 4 | `RestTransport.uploadFile` | `rest-transport.ts:223` | 同上（尾参追加，源兼容） |
- **Operation 契约**：`Transport.execute` 的操作参数字面量新增可选 `bearerToken?: string`（与 `sessionKey?` 并列；四处内联字面量类型同步——transport.ts:51-60 / base-http-transport.ts:32-39 / transport.ts:77-85 / rest-transport.ts:96-103）。
- **透传链（M6：原方案漏项）**：
  - `ServiceProxy`（原方案"不动"，现**必改**）：`ServiceProxyOptions` 增 `bearerToken?: string | null`；`createUse()` 构造（service-proxy.ts:150）同步透传。
  - `DomainClientUser.Use()`（:478）构造 ServiceProxy 时传 `bearerToken: this.externalSession?.accessToken`。
  - `DomainClientUser.query()/mutate()/ping()` + `QueryBuilder`（query-builder.ts:234 `_sessionKey` 同一快照点）须透传 `bearerToken`。
- **refreshJwt()（M7 整改：错误分层 + body 显式）**：
  ```typescript
  /** V1.0.12：外部会话显式续期（P5 显式，不做自动隐式 refresh）。
   *  成功 → 更新 externalSession 持久化；403/400/404（refresh 失效或已撤销）→ 清 externalSession + 抛 JWT_SESSION_INVALID；
   *  网络失败（NETWORK_ERROR）→ 保留 externalSession（access 仍可用至过期）——S4 语义分层。 */
  async refreshJwt(signal?: AbortSignal): Promise<ExternalLoginResult>
  ```
  - 内部经同 REST 专用通道：`POST {base}{urlMap["refreshToken"] ?? "/api/auth/refresh"}`，body = `JSON.stringify({ refreshToken: this.externalSession.refreshToken })`——**camelCase 显式契约**（M7，非依赖 JS 默认字段名的隐式行为）。
  - **错误语义分层**：refresh 端点 4xx（refresh token 失效/被撤销，服务端返 400 而非 401）→ `JWT_SESSION_INVALID` + 清 externalSession（强制重登，不触发 onUnauthorized 二次，防循环）；**access 401 → `AUTH_EXPIRED`**（既有 transport 归一，refresh 可能仍有效，调用方可选调 refreshJwt() 续期）——两错误码**可区分**，调用方据此决定 retry vs re-prompt（而非"统一 onUnauthorized 兜底"）。`AUTH_EXPIRED` 仍触发 onUnauthorized（兼容现有行为）。
- **storage 策略（M8 整改）**：JWT 会话持久化沿用消费方配置的 storage（SDK 不静默改配置），但**默认建议 + 文档化**：
  - README §1.2 storage 表新增行："JWT 外部 IdP 会话（v1.0.12+）：默认 sessionStorage；refresh token 30d 生命周期，localStorage 持久化需自行评估 XSS 暴露风险（bearer 被窃取即 30 天有效，与可单点吊销的 sessionKey 不同）"。
  - 本迭代不实现 HttpOnly cookie 存储（需服务端 Set-Cookie 配合，归开放项）。

### 2.4 外部登录辅助（M2/M5/S3 整改）

```typescript
/** V1.0.12：解析 OAuth 回调 URL（location.search / 显式 URL）→ { code?, state?, error?, errorDescription? }。
 *  内部委托 QueryString.parse（不新增 query string 解析双源——S3）；
 *  纯工具（无副作用、不导航、不持久化）——导航/跳转编排归消费端（P5）。 */

```

- **删除 `buildExternalLoginUrl`（M2/M5）**：Federation 服务端已提供权威 `authorize_url`（`POST /feberation/authorize/start` 返回 `new { authorize_url, state }`），SDK 客户端拼 OAuth URL = 复制服务端唯一权威职责（P2 违反）+ 把平台知识（scope 默认 snsapi_base）硬编码进通用 SDK（P8 违反）。方案原 §2.4"Federation `POST {prefix}/{platformId}/login` 返回 authorize_url"系**契约误归属**（该端点返回 `SsoChannelAuthResult`）——本稿已删除该函数及错误引用。
- **实现位置**：不新建 `src/external-login.ts` 独立文件（原方案的 build/resolve 双函数文件已无存在必要）——`resolveOAuthCallback` 作为 `QueryString` 预设配置落在 `src/query-string.ts`（导出 `OAUTH_CALLBACK_FIELDS` 预设 + `resolveOAuthCallback` 便捷包装，内部委托 QueryString.parse）。

### 2.5 错误码/异常语义（M10 整改）

| 场景 | ErrorCode | HTTP 映射（服务端已有） |
|------|-----------|------------------------|
| 通道类型空/空白（前置守卫） | `INVALID_ARGUMENT`（新客户端码） | 不送服务端 |
| 缺 code / ticket（前置守卫） | `INVALID_ARGUMENT`（新客户端码） | 不送服务端 |
| 认证失败（验签/code 无效，服务端 FailReason 透传 message） | `AUTH_FAILED` | 400 |

| 外部登录传输失败（无 REST 通道/网络失败） | `EXTERNAL_LOGIN_FAILED`（新客户端码） | — |
| JWT 会话响应缺 AccessToken / wire casing 错误 | `JWT_SESSION_INVALID`（新客户端码） | — |
| refresh 4xx（refresh token 失效/被撤销） | `JWT_SESSION_INVALID`（清 externalSession） | 400 |
| access 过期（既有行为不变） | `AUTH_EXPIRED` | 401 |

- **新客户端码落点（M10）**：`INVALID_ARGUMENT` / `EXTERNAL_LOGIN_FAILED` / `JWT_SESSION_INVALID` 三条加入 `src/domain-client-error.ts` 的 `ErrorCode` union 类型（与 `AUTH_EXPIRED`/`SERVER_ERROR` 等客户端独有码同位，:7-14）；**零手改 `src/generated/error-codes.ts`**（该文件为 auto-generated + 服务端码映射，P10 防绕过）。v1.0.11 的生成物机制是 `operationKinds`（schema-parser 产物），与 error-codes 无生成链路——本迭代不假借其名手改生成物。
- 服务端 FailReason 经 `DomainClientError.message` 机器可读透传（`SsoChannelAuthResult.FailReason` 语义）。

## 6. 向后兼容与开放项

**向后兼容**：
- 全部新增项为**可选**（不配置 `restUrlMap["loginByExternal"]` 仅影响显式调用新 API）；既有 `sessionKey` 会话路径零改动（persist 增量追加 externalSession 键，旧数据无该键 → restore 走 sessionKey 分支）
- `loginByExternal`/`refreshJwt` 是新方法，不影响既有登录族；不在 `EXPLICIT_MUTATIONS` 中（经 RestTransport 专用路径，不经 ServiceProxy）
- Transport 接口兼容扩展（可选能力方法 `loginByExternal?` + Operation `bearerToken?` 可选；`executeRawGraphQL`/`uploadFile` 尾参追加源兼容）
- `generated/error-codes.ts` 零改动（P10）

**开放项（不在本迭代范围）**：
1. **事件取 OpenId 的 SPA 落地端点**（扩展侧 `v0.10.0` 方案）：`loginByExternal("ticket", { ticket })` 通用形态已预留，待服务端端点落地后消费端接线即可（本迭代不写死 ticket 专用 API）。
2. **自动 refresh（静默续期）**：本迭代提供 `refreshJwt()` 显式 API；自动续期策略（401 拦截自动 refresh + 重放）归未来迭代（需评估重放幂等/并发单飞；**且需评估 refresh token XSS 暴露时长——refresh 30d 长生命，建议自动续期仅刷新 access(2h)，refresh 持久化仍 sessionStorage**——M8 增注）。
3. **OAuth 回调导航编排 + authorize 发起**：SDK 只提供 `resolveOAuthCallback` 纯解析预设；跳转路由（微信授权页发起/回调落地后的 router 跳转）归消费端；服务端 authorize 端点（`POST /feberation/authorize/start`）是否封装为 SDK 方法（`getExternalAuthorizeUrl`）评估后归未来迭代（M5 替代设计；注意 RoutePrefix 拼写 `/feberation`——S1）。
4. **sessionKey 会话与 externalSession 会话互转**：设计上两形态独立并存、不隐式互转（P2 单一源）；未来若服务端提供统一会话桥再评估。
5. **JWT 会话与 RpcCache 互操作（S5）**：RpcCache 会话分桶键 `[scenario, sessionKey, field, variables, selection]` 在 JWT 会话下 sessionKey 为 null——设计意图：JWT 会话分桶键应使用 `externalSession.accessToken`（或其 hash）作桶键，避免两形态缓存串扰；不在本迭代实施，方案声明意图防返工。
6. **服务器端 `login/external` 的 FailReason 全量错误码对齐**：扩展侧 V0.10.0 方案统一（含 `ticket` 通道）——本 SDK 迭代错误表按服务端现状先收敛。
7. **HttpOnly cookie 存储 JWT**：需服务端 Set-Cookie 配合，消费方/服务端联合评估（M8 范围控制）。
