# tkwf-tsclient 发布流程与操作经验

> 归档用途：后续所有版本发布按本文档执行。来源：v1.0.8 ~ v1.0.14 各次发布实测经验（含踩坑记录）。
> 配套：`Agents_TKWF.md` §4（Tag 与发布纪律）为规则权威，本文档为操作手册。

---

## 一、发布前置：迭代闭环完成

按 `Agents_TKWF.md` §3 完整闭环执行后才允许发布：

1. 开发方案 + Oracle 方案审核（必修项 M# 全部纳入）
2. 实施编码（测试 + build 通过）
3. 审核报告 + Oracle 代码审核（复杂设计必做）
4. Sisyphus 亲自复审（验证清单 + 全量测试 + 构建）
5. 提交 + push（**不 tag**）

发布前的硬性检查：

```bash
git status --short        # 工作区干净（忽略 .omo/ pnpm-lock.yaml 等本地文件）
npm test                  # 全量测试（当前 379 条，随迭代增长）
npm run build             # tsc 0 错误
git log --oneline <上一tag>..HEAD   # 确认未发布提交的内容（不得包含未审核/未完成的半成品）
npm view @tkwf/tsclient version      # 确认目标版本尚未在 registry
```

## 二、发布版本号确定

- 语义化版本，**子版本号（patch）升级**：`v1.0.x → v1.0.(x+1)`（如 1.0.13 → 1.0.14）
- `package.json` 的 `version` 字段与 `git tag` **必须一致**（tag 触发 publish workflow，发布的就是 package.json 里的版本）
- 版本号与内容匹配原则：每个已推送的功能/修复提交组对应一个版本；同一主题的失败尝试/探索性改动合并后再发布

## 三、发布操作步骤

```bash
# 1. bump 版本号（只改 package.json version 字段）
#    修改后：npm test 不重跑（无代码变化），但建议快速确认 build 产物引用正常

# 2. 提交版本号（提交纪律：与发布文档合并或独立 release commit 均可，
#    仓库既有风格：git commit -m "release: v1.0.14" 或 feat/fix 内嵌版本号）
git add package.json docs/发布流程与操作经验.md
git commit -m "release: v1.0.14"
git push origin master

# 3. 打 tag 并推送（触发 GitHub Actions Publish）
git tag v1.0.14
git push origin v1.0.14

# 4. 检查 workflow（publish.yml：npm ci → npm publish --access public --provenance）
gh run list --workflow=publish.yml --limit 3
gh run view <run_id> --json status,conclusion
gh run view <run_id> --log-failed   # 失败时看日志

# 5. 确认 npm 发布成功（注意传播延迟，见 §五 经验1）
npm view @tkwf/tsclient version           # → 1.0.14
npm view @tkwf/tsclient dist-tags --json  # latest 应为新版本
```

## 四、发布触发机制（GitHub Actions）

- `.github/workflows/publish.yml`：`push: tags: [v*]` 触发
- 流程：`npm ci` → `npm publish --access public --provenance`
- **provenance（Sigstore 签名）**：workflow 声明了 `permissions: id-token: write`；签名产物标记发布来源——因此**必须由 CI 发布**，本地手动 `npm publish` 会丢失 provenance 且可能触发 OTP/权限问题
- 认证：`NPM_TOKEN` secret → setup-node 的 `registry-url: https://registry.npmjs.org/`
- 关联包：`@tkwf/tsclient-mock` 为**独立仓库**维护（版本流水独立，当前 1.4.x），不随本仓库 tag 发布

## 五、操作经验与踩坑记录

### 1. npm registry 传播延迟（高频）
- 现象：GitHub Actions `conclusion: success` 后立即 `npm view` 报 404（`No match found for version`）
- 原因：npmjs 发布后 registry 索引传播/缓存有延迟（实测 60~120 秒）
- 处理：**不要判定失败**，等待 60~120s 后重查 `npm view ... dist-tags --json`；workflow success + 延迟重查确认 404 消失才叫发布成功
- 教训记录（v1.0.10）：`gh run view` success 后首查 404 → 60s 后即 `latest: 1.0.10`，属正常现象

### 2. tag 与版本号的强绑定
- tag 名 = `v` + package.json version，**严格一致**；不一致时 npm 发布的版本与 tag 语义脱离，回查历史困难
- 若 tag 打错/重复：`git tag -d vX.Y.Z && git push origin :refs/tags/vX.Y.Z` 后重打；已触发 workflow 的 tag 删除不会撤销已完成的发布
- 发布前先 `git tag --sort=-v:refname | Select-Object -First 5` 确认目标 tag 不存在

### 3. 发布前置干净度
- 发布提交只包含**本迭代相关文件**：`git add` 逐个指定，不用 `git add -A`（防混入 `.omo/`、`pnpm-lock.yaml` 等本地生成物）
- 若工作区有未跟踪杂项，先确认其不在提交范围；仓库以 npm 为准（`package-lock.json` 提交，`pnpm-lock.yaml` 不提交）

### 4. gh CLI 可用性与限流
- 国内网络环境 `gh` 命令偶发超时/rate limit：可重试；`gh run list` 无输出时用 `gh run list --workflow=publish.yml --limit ≥1` 显式指定 workflow
- 替代方案：GitHub.com 仓库页面 → Actions 标签页直接看 run；不用 gh 也能完成流程（tag push 即触发）

### 5. workflow 失败排查
- 最常见失败点：npm publish 认证（NPM_TOKEN 过期/未配置）、版本重复（registry 已有该版本 → 409）
- 处置：查看 `--log-failed`；认证问题由仓库管理员更新 secret；版本重复则 bump 新版本号，**不要删除已发布的版本**
- 发布是**不可逆动作**（npm 不允许覆盖同版本号），发布前确认代码已完成全量测试

### 6. 双包联动注意
- `@tkwf/tsclient` 升级后，`@tkwf/tsclient-mock`（独立仓库）可能需要跟随升级（peer 兼容）
- 消费端项目（如 DMP-Lite / WebH5）依赖固定版本或 `^` 范围：发布后应通知消费端更新；codegen 产物（`domain-client.g.ts` 等）由消费端工具链生成，不走 npm

### 7. 历史记录参考
- v1.0.8/1.0.9/1.0.10：各次发布的 workflow 耗时 22~23s（`gh run list` 历史可见）
- 发布 commit 风格：`release: vX.Y.Z`（v1.0.7/1.0.13 先例）；功能/修复提交内嵌版本号（v1.0.8→1.0.9 先例）——两种均可，但 **release commit 必须只含版本号/发布文档改动**

## 六、发布后收尾

1. `npm view @tkwf/tsclient dist-tags --json` 确认 `latest` = 新版本
2. 若本次包含消费端行为变更（如 v1.0.10 variableTypesMap、v1.0.11 operationKinds）：提醒消费端更新依赖 + 重新 codegen
3. 更新本文档的经验记录（如有新坑）——归档可持续演进
